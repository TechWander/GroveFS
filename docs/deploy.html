GroveFS 部署与命令实操演示

本页是面向上手实操的独立教程：第一部分给出三套部署的拓扑与步骤（每套都先设定好节点数、硬盘数等示例环境，命令可直接照抄后改地址）；第二部分在每套部署上按功能划分演示全部常用命令——建基视图、授权、四种视图（基 / 派生 / 别名 / fork）的创建与验证、配置文件写法、日常运维。

本机部署 = 1 台机器 · 3 个进程（两个服务 + 一次挂载） SQLite 分布式 = 1 台存储机 + N 台客户机 PG 分布式 = 元数据进 PostgreSQL 示例环境均为虚构内网 10.0.0.x

约定：下文 $G 指 GroveFS 可执行文件（./target/release/grovefs 或安装后的 grovefs）。三套部署使用同一个二进制，差别只在「元数据存哪、谁起服务」。端口约定：数据服务 50100、元数据服务 50110。所有示例 IP 为虚构内网地址，照抄时替换为自己的。

第一部分 · 三套部署方法

三套部署的差别，一句话说清：本机部署把两个服务与挂载放在同一台机器上（地址写 127.0.0.1），三进程起步；SQLite 分布式把存储与元数据拆到一台存储机的两个中心服务（data-server + meta-server），客户机远程挂载、本地什么都不落；PG 分布式只改 meta-server 一处——把元数据从本地 SQLite 文件换成 PostgreSQL 库，客户机挂载命令一字不差。三套共用同一个挂载命令形态：挂载只把 --manager 指向部署的引导服务，元数据/数据两个坐标都由它签发的 roster 解析——手敲 --meta-server/--data-servers 直连已从 mount 移除，没有 manager 引导就非零退出，「只给一个目录就挂上」的形态更不存在。

1.1 本机部署（三进程同机，最小集群）

示例环境：一台开发机（8 核 / 32GB / 1TB NVMe），操作系统 Linux，已安装 GroveFS 二进制。数据与元数据全部落在同一块盘的 /data/gfs 目录下。三个进程都要起来——data-server 管字节、meta-server 管权威树、mount 是第三个进程；127.0.0.1 上的两个端口就是它的「集群网络」。不需要安装数据库：元数据是内嵌 SQLite（编译进二进制，零外部依赖），字节直接写本地对象目录。

存储根（起步时让 meta-server --meta-dir 与 data-server --data-dir 指向同一个目录）的内部结构由 GroveFS 自动维护，无需预建：

/data/gfs/
├─ blocks/<2hex>/<key>   # 文件字节：按 key 哈希分 256 个桶目录，key 是 UUID
└─ meta/
   ├─ <视图名>/            # 每个物理视图一棵权威树，自成一个目录（ls meta/ 列出的就是树）
   │   └─ <视图名>.db       # 树本体：node/ctrl/locks 三张表（-wal/-shm 同目录，随 checkpoint 出没）
   ├─ _control/             # 控制面，不是树：refs.db 跨视图持有账本 · api_keys.db 密钥与审计 · store.key
   ├─ views/<名>.layout    # 派生/别名/fork 的定义文本（纯文本，可手改可 git diff）
   └─ .xfer/                # export/import 的服务端暂存区（点开头，永不是树）

部署步骤（建视图 → 声明拓扑的 manager → 两个服务注册 → 挂载）

# 1) 建基视图（显式创建——挂载从不自动建树，名字不存在直接拒绝，无开关）
$G view --meta-dir /data/gfs create --view team
# created BASE view 'team' at /data/gfs/meta/team/team.db

# 2) 起引导服务 manager：先声明这台集群的拓扑，再 serve（首次 serve 铸 join.key/roster.key 于 /data/gfs/manager/）
$G --home /data/gfs manager define --meta 127.0.0.1:50110 --data 127.0.0.1:50100
$G --home /data/gfs manager serve --listen 127.0.0.1:50055 &
# manager listening on 127.0.0.1:50055 (host-readable state /data/gfs/manager/deployments.json)

# 3) 数据服务（管字节），顺手向 manager 注册；前台阻塞单独一个终端，验证过了再交给 systemd（2.2.1）
$G data-server --listen 127.0.0.1:50100 --data-dir /data/gfs \
     --advertise-addr 127.0.0.1:50100 --register-with 127.0.0.1:50055 --join-key-file /data/gfs/manager/join.key
# data-server listening on 127.0.0.1:50100 (host <机器名>, 1 data root(s): /data/gfs)

# 4) 元数据服务（托管权威树），同样向 manager 注册
$G meta-server --meta-dir /data/gfs --listen 127.0.0.1:50110 \
     --advertise-addr 127.0.0.1:50110 --register-with 127.0.0.1:50055 --join-key-file /data/gfs/manager/join.key
# meta-server listening on 127.0.0.1:50110 (base /data/gfs, role Primary)

# 5) 挂载（默认转后台：挂载点就绪即返回）——坐标只从 manager 解析，本机也不手抄两个地址
$G mount --view team -m /mnt/team --manager 127.0.0.1:50055 --roster-key-file /data/gfs/manager/roster.key
验收：挂载先打印一行 roster 解析 manager 127.0.0.1:50055: deployment 'default' epoch 1 resolved meta [127.0.0.1:50110] data [127.0.0.1:50100] (signature verified, valid for …s more)，再打印 using remote metadata service at 127.0.0.1:50110、using remote data service at 127.0.0.1:50100、mounting view 'team' at /mnt/team (fully remote: no local store)，最后一行带后台进程号 grovefs: mounted view 'team' at /mnt/team (background pid …)。然后 mkdir -p /mnt/team/docs && echo hello > /mnt/team/docs/a.txt && cat /mnt/team/docs/a.txt 输出 hello；ls /data/gfs/blocks | head 能看到哈希桶目录（00 01 02 …）——字节确实落在存储根，不在挂载点。卸载用 $G umount -m /mnt/team（打印 unmounted /mnt/team，同时收掉后台挂载进程，别用系统 umount 命令）。

本机部署（三进程同机）的特点：

维度本机部署的行为
元数据内嵌 SQLite，一视图一棵独立树目录 meta/<名>/<名>.db，无需安装任何数据库；打开它的只有 meta-server 进程，客户端一个字节都不持有
写入模型单写者（同一时刻一个写事务）；读走 WAL 可并行
挂载坐标两个地址都从 --manager 的签名 roster 解析。不给 --manager/--roster-key-file → 退出码 1（a mount resolves its cluster coordinates from the deployment's manager …），不猜地址、不降级成直连本地目录
准入由服务端把关：不带 --token 时任何能连上这两个端口的本地进程都能挂任何视图，所以最小自觉是把 --listen 绑在 127.0.0.1；再往里才是挂载点自己的 OS 权限
多用户任意多个基视图各自一棵树互不可见；派生/别名/fork 在本机同样全部可用（见 2.1.3）
边界单写者、单进程组；把两个服务的 --listen 换成内网地址、客户机把 127.0.0.1 换成存储机 IP，命令形态一字不变就是 1.2 的分布式部署

1.2 SQLite 作为后端的分布式部署

示例环境：共 3 台机器的内网（10.0.0.0/24）。
· node1（10.0.0.5）——存储中心：4 块 8TB HDD（系统盘之外组一个数据盘挂 /data/cluster），跑 data-server（管字节）+ meta-server（管元数据），两个服务同机同盘起步；
· node2（10.0.0.6）——客户机 A：读写挂载，不落任何数据；
· node3（10.0.0.7）——客户机 B：读写/只读挂载，不落任何数据。
后置扩展（可选）：加 node0（10.0.0.4）做 meta-server 主备 HA；或让 node0 兼任第二台 data-server 做条带聚合。 
          ┌────────────── node1 (10.0.0.5) 存储中心 ──────────────┐
          │  /data/cluster（4×8TB 数据盘）                        │
          │   ├─ blocks/   ← data-server :50100 收到的字节         │
          │   └─ meta/     ← meta-server :50110 托管的权威视图树    │
          └──────────────┬───────────────────────┬───────────────┘
                 50100+50110 │                       │ 50100+50110
                   ┌─────────┴─────────┐   ┌─────────┴─────────┐
                   │ node2 10.0.0.6    │   │ node3 10.0.0.7    │
                   │ 客户机 A（读写）    │   │ 客户机 B（读写/RO） │
                   │ 本地不落盘         │   │ 本地不落盘         │
                   └───────────────────┘   └───────────────────┘

多机共享一棵树的能力来自「同一个 meta-server + 同一个 --view」，与后端无关——默认 SQLite 已经足够，PG 不是分布式的前提。拆开的两个服务各管一摊：

服务职责关键参数
data-server收发文件字节，把物理对象写进本节点硬盘目录--listen、--data-dir、--token、--require-api-key（配 --meta-dir 读注册表）、--data-access-key（校 OP_OPEN 能力，与 meta 同值）
meta-server托管每视图权威树，多客户机挂同一 --view 即共享同一棵；负责锁仲裁、失效推送、API key 门--listen、--meta-dir（元数据根，视图库在其 meta/ 下）、--token、--require-api-key、--data-access-key/--data-access-ttl（签 M_OPEN 能力）、HA 时 --role/--peer/--witness
客户机 mount挂载：只有远程形态，坐标一律由 manager 签发的 roster 解析，本地不落任何权威数据--view、--manager + --roster-key-file（坐标的唯一来源）、--deployment、--token/--api-key、--ro（--meta-server/--data-servers 已从 mount 整体移除）

部署步骤（node1 上：建视图 → 声明拓扑的 manager → 两个服务注册）

# 0) 生成共享 token（强烈建议；三台机器用同一个值）
TOK=$(head -c 24 /dev/urandom | base64)

# 1) 先建基视图，再起服务（视图只能显式创建——不建就挂会被拒，且什么都不写）
$G view --meta-dir /data/cluster create --view team

# 2) 起引导服务 manager：声明拓扑，两个坐标都从这里签发（首次 serve 在 <state-dir>/manager/ 铸 join.key/roster.key）
$G --home /srv/mgr manager define --name prod --meta 10.0.0.5:50110 --data 10.0.0.5:50100
$G --home /srv/mgr manager serve --listen 0.0.0.0:50055 &

# 3) 数据服务：把对象存到本节点数据盘，顺手向 manager 注册（对外坐标用 --advertise-addr）
$G data-server --listen 0.0.0.0:50100 --data-dir /data/cluster --token "$TOK" \
     --advertise-addr 10.0.0.5:50100 --register-with 10.0.0.5:50055 --join-key-file /srv/mgr/manager/join.key --deployment prod

# 4) 元数据服务：托管权威视图树，同样注册
$G meta-server --meta-dir /data/cluster --listen 0.0.0.0:50110 --token "$TOK" \
     --advertise-addr 10.0.0.5:50110 --register-with 10.0.0.5:50055 --join-key-file /srv/mgr/manager/join.key --deployment prod

生产环境把两个服务写成 systemd 常驻单元（grovefs-data.service / grovefs-meta.service，token 走 EnvironmentFile 指向的 root-only env 文件，不进命令行），并只对内网网段开放 50100/50110 两个端口。

客户机挂载（node2 / node3）

# 挂载不需要 --home，本地不落任何权威数据；坐标只从 node1 的 manager 解析（roster key 从 node1 拷来，客户端永不持 join.key）
export GROVEFS_TOKEN=<与 node1 相同的串>
$G mount --view team -m /mnt/team \
     --manager 10.0.0.5:50055 --deployment prod --roster-key-file /etc/grovefs/roster.key          # 读写
$G mount --view team -m /mnt/team_ro \
     --manager 10.0.0.5:50055 --deployment prod --roster-key-file /etc/grovefs/roster.key --ro     # 本机只读（服务端硬只读另见 2.2.3）
验收（node2 写、node3 立刻读）：node2 上 echo x > /mnt/team/t.txt，node3 上 cat /mnt/team/t.txt 在 2 秒内可见——失效推送是实时的，无需轮询、无需重挂。分布式锁也跨机生效：flock -x /mnt/team/lk -c 'sleep 30' 期间，另一台 flock -x /mnt/team/lk -c 'echo got' 会等前一个退出才打印。

可选扩展 A：meta-server 主备 HA（加 node0）

# node1（10.0.0.5）：主，读写，周期推快照给备；两节点各用独立的 --meta-dir
$G meta-server --meta-dir /data/cluster --listen 10.0.0.5:50110 \
     --role primary --peer 10.0.0.4:50111 --token "$TOK"
# node0（10.0.0.4）：备，只读服务，主心跳丢失后自动提升
$G meta-server --meta-dir /data/ha     --listen 10.0.0.4:50111 \
     --role standby --peer 10.0.0.5:50110 --token "$TOK"

# 故障转移列表写进 manager 的 --meta（有序：首位就是主），客户机只指 manager，主挂自动切备
$G --home /srv/mgr manager define --name prod --meta 10.0.0.5:50110,10.0.0.4:50111 --data 10.0.0.5:50100
$G mount --view team -m /mnt/team --manager 10.0.0.5:50055 --deployment prod --roster-key-file /etc/grovefs/roster.key

默认异步复制 RPO≈500ms（极端故障丢最后半秒内的写）；加 --sync-repl 把 RPO 降到 0（写返回前等备落盘 ACK）；加 --witness <data-server 仲裁者列表>（推荐奇数个）获得真 fencing：组不成多数派租约时冻结写而非双写。诚实边界：严格两节点不配 witness 时无法防脑裂，这是 CAP 硬边界。

可选扩展 B：多 data-server 条带（聚合容量）

# 让 node0（10.0.0.4）也跑一台 data-server，配稳定成员 id（消除列表顺序隐患）
$G data-server --listen 0.0.0.0:50100 --data-dir /data/cluster2 --member-id 2 --token "$TOK"
# 把完整成员集写进 manager 的 --data → 大文件（≥16MiB）自动确定性条带；小文件只落一台
$G --home /srv/mgr manager define --name prod --meta 10.0.0.5:50110 --data 10.0.0.5:50100,10.0.0.4:50100
$G mount --view team -m /mnt/team --manager 10.0.0.5:50055 --deployment prod --roster-key-file /etc/grovefs/roster.key

扩展 C：挂载引导 manager 的细节（集中声明拓扑、节点注册与 roster 语义）

它把拓扑声明集中到一处：以前每台客户机都要手抄一遍 --meta-server（有序故障转移列表）与 --data-servers（分条成员全集）——现在这两个坐标都收进 manager define 一次声明。operator 在 define 里定死列表与顺序，node0（10.0.0.4）上跑一个 manager serve：应答签名，客户机只指它一个地址，拿回同一对坐标后直连两个服务——manager 从不在 IO 路径上；手敲 --meta-server/--data-servers 已从 mount 整体移除，不存在「逐机抄坐标」这条路了。 
# node0：声明拓扑（写进 <state-dir>/manager/deployments.json），再起引导服务
$G manager --state-dir /srv/mgr define --name prod \
     --meta 10.0.0.5:50110 --data 10.0.0.5:50100
$G manager --state-dir /srv/mgr serve --listen 0.0.0.0:50055
# 两份 key 就落在 /srv/mgr/manager/{join,roster}.key（0600，首次 serve 铸造）

# node1：两个服务起时顺手注册自己（join key 从 node0 拷来，客户端永不持有它）
$G data-server --listen 0.0.0.0:50100 --data-dir /data/cluster --member-id 0 --token "$TOK" \
     --register-with 10.0.0.4:50055 --advertise-addr 10.0.0.5:50100 \
     --join-key-file /etc/grovefs/join.key --deployment prod
$G meta-server --meta-dir /data/cluster --listen 0.0.0.0:50110 --token "$TOK" \
     --register-with 10.0.0.4:50055 --advertise-addr 10.0.0.5:50110 \
     --join-key-file /etc/grovefs/join.key --deployment prod

# node2 / node3：只指一个地址（roster key 从 node0 拷来）
$G mount --view team -m /mnt/team --manager 10.0.0.4:50055 --deployment prod \
     --roster-key-file /etc/grovefs/roster.key
四条语义决定它能不能替你把事情做对：① roster 是声明集，不是健康子集——用了扩展 B 的条带就必须在 define --data 里把两个地址都写全（声明时少写一个地址，挂载读到分条对象会显式 EIO，不会静默给你一个空文件），而「声明了但没起」的 data-server 会让挂载失败而不是被跳过；② 注册不是准入——节点连不上 manager 照常服务，退避重连（按状态变化而不是按次打日志）；③ 未声明的地址进不来——join key 泄露也插不进攻击者的机器，一条注册只在 define 声明过的地址上生效；④ 验不过就拒挂——缺 roster key、签名不符、roster 过期一律退出非零，不「先挂上再警告」。

--manager 已是 mount 的唯一坐标来源：手敲的 --meta-server/--data-servers 已从 mount 整体移除，所以不存在「两者并存或互斥」——只余这一条路（一次挂载只有一个真值来源）。roster 解析出的地址列表直接喂进与旧时同一对值，故障转移与条带语义不变。杀掉 manager 不动任何已有挂载，只让新挂载 fail-closed；运维侧用 manager status --server 10.0.0.4:50055 --deployment prod --join-key-file /etc/grovefs/join.key 逐地址看谁注册了、报了什么 member-id。serve --require-registered 是预检门——开了以后「声明了但没注册」的成员会让整刀 lookup 被拒而不是被跳过，roster 本身仍不收缩成健康子集，默认关。逐参数语义、否决项与残余风险见 docs.html §4.2 与 docs/adr/0001-manager.md。

1.3 PostgreSQL 作为后端的分布式部署

示例环境：共 4 台机器。
· db1（10.0.0.9）——独立 PG 服务器：16 核 / 64GB / 2TB NVMe，PostgreSQL 16，max_connections=200；只跑数据库，客户机与服务机都不装 PG；
· node1（10.0.0.5）——存储中心：同 1.2（4×8TB 数据盘），跑 data-server + meta-server；meta-server 改连 db1，本地不落任何权威元数据；
· node2（10.0.0.6）/ node3（10.0.0.7）——客户机，同 1.2。
后置扩展（可选）：加 db2（10.0.0.11）做第二个 PG 实例，走「实例注册表 + 视图放置」扩容（2.3.6 演示）。

三条硬规则：① 视图必须显式创建（两种后端同一纪律），且 PG 下视图名 ≤ 25 字节（PG 标识符 63 字符上限，hex 编码翻倍；中文约 8 个字）；② --meta-store 与自研 HA 的 --role/--peer/--witness 互斥，同时给启动即失败——PG 档的高可用交给 PG 自身的流复制 / PITR；③ 连接串别进命令行（argv 在 ps 里全网可见），生产做法见 2.3.2 的 env 文件。

维度SQLite（1.2）PostgreSQL（1.3）

独有命令目录零拷贝 import、离线 gc 扫本机 blocks、原生 HA无（同名命令不同壳：--meta-dir 换 --meta-store）

1.4 存量存储根升级到 v2 布局（一棵树一个目录）

本版 GroveFS 的元数据布局是 v2：每棵物理视图树自成一个目录 meta/<视图名>/<视图名>.db，控制面集中到 meta/_control/，派生/别名定义在 meta/views/*.layout——目录名就是类型，ls meta/ 列出的就是树（1.1 的存储根图就是这个形态）。老的 v1 扁平形态（meta/ 下平铺 team.db/refs.db）没有命令读它：换新二进制后，任何要读视图树的命令都会拒绝并指名迁移动词。

2.1 本机最小集群 · 命令演示

场景沿用 1.1：一台 devbox，存储根 /data/gfs，两个服务听 127.0.0.1:50110（元数据）与 127.0.0.1:50100（数据）。演示团队视图 team 与个人视图 alice。

2.1.1 建基视图

基视图是真正存数据的物理树，建树只有一条显式入口：view --meta-dir D create --view V（顶层 import 顺带建，见 2.2.2）。最常见的误解是「往挂载点里写文件 = 建视图」——不是：写入只是往已存在的树里加节点，名字不存在时 meta-server 直接拒绝这次挂载，从不自动建空树。

$G view --meta-dir /data/gfs create --view team      # 建团队基视图 → /data/gfs/meta/team/team.db
# created BASE view 'team' at /data/gfs/meta/team/team.db

# 用种子清单一次性铺好目录骨架（每行 mkdir / touch 两种指令，# 注释，幂等可重跑）
cat > seed.txt <<'EOF'
mkdir docs
touch docs/README.txt
mkdir photos
EOF
$G view --meta-dir /data/gfs create --view alice --manifest ./seed.txt   # 第二个视图；两棵树互不可见
# created BASE view 'alice' at /data/gfs/meta/alice/alice.db
# applied seed manifest ./seed.txt
# 名字不存在：这次挂载被拒，退出码 1，服务端什么都不建
$G mount --view ghost -m /mnt/ghost --manager 127.0.0.1:50055 --roster-key-file /data/gfs/manager/roster.key
# manager 127.0.0.1:50055: deployment 'default' epoch 1 resolved meta [127.0.0.1:50110] data [127.0.0.1:50100] (signature verified, valid for …s more)

# using remote data service at 127.0.0.1:50100

坐标不再由挂载命令携带：给 mount 递 --meta-server/--data-servers 已是未知参数（clap 直接报错退出）；而漏给引导（缺 --manager 或 --roster-key-file）挂载立刻以 error: a mount resolves its cluster coordinates from the deployment's manager: there is no longer a way to name a metadata or data service by hand. … 退出 1——不猜地址，也不退回「直连本地目录」。注意 --home 从挂载命令里消失了：它是节点侧动词与两个服务的存储根，挂载从不读它，本机档也一样（挂载点目录里除了 FUSE 什么都不落）。

为什么是删除而不是「降级为仅测试用途」，以及移除后剩下的遗留（引擎批接口暂无生产调用者），见 docs/adr/0002-no-local-mount.md。

后台挂载的输出追加进日志文件（默认 $TMPDIR/grovefs-mount-<挂载点>.log）；systemd/调试场景用 --foreground 保持终端附着，Ctrl-C 即卸载。

① 派生视图（只读透镜）：规则文件是纯文本，四个动词 only / hide / map / link。

cat > docsonly.rules <<'EOF'
# 只显示 /docs 子树
only /docs
EOF
$G view --meta-dir /data/gfs define --name docsonly --base team --rules docsonly.rules
# 输出: defined derived view 'docsonly' over base 'team': 0 hide, 1 only, 0 reloc rule(s)
# note: mounts of 'docsonly' are read-only (virtual shape) — write to base view 'team'
$G mount --view docsonly -m /mnt/lens --manager 127.0.0.1:50055 --roster-key-file /data/gfs/manager/roster.key &
# 只给派生名，不带 --layout：只读契约由 M_OPEN 握手从服务端带回来
# derived view 'docsonly' over base 'team': read-only lens
# mounting view 'docsonly' at /mnt/lens (fully remote: no local store, read-only)
ls /mnt/lens            # docs            ← 只有 docs，其余子树连存在性都不泄露
echo x > /mnt/lens/docs/new.md
# bash: Read-only file system   ← 派生一律只读（硬契约）；写走基名 /mnt/team

② 纯别名（公开名，全树可写）：挂别名 = 挂真实视图；别名存在期间，真实名 team 从此不可直挂（meta-server 拒）。定义可以在基视图正挂着的时候下，不用先卸载。

$G view --meta-dir /data/gfs alias --name pub --real team
# defined pure alias 'pub' -> real view 'team'
# note: 'team' is no longer a mount entry point while this definition exists (the meta-server refuses a mount of the real name); alias mounts show the FULL tree and are WRITABLE
$G mount --view pub -m /mnt/pub --manager 127.0.0.1:50055 --roster-key-file /data/gfs/manager/roster.key &
# alias view 'pub' resolves to real view 'team' (full tree, writable)
echo hello > /mnt/pub/docs/note.md      # 可写；写入即落在 team 的同一棵树上
cat /mnt/lens/docs/note.md              # hello   ← 从只读透镜 /mnt/lens 立刻读到同一份

# 真名此时挂不上——拒的是名字，不是挂载状态（基视图还挂着也照样拒）
$G mount --view team -m /mnt/t --manager 127.0.0.1:50055 --roster-key-file /data/gfs/manager/roster.key
# error: view 'team' is governed by an alias — mount the alias name instead (`grovefs view list` shows it)

# 公开名泄露后一条命令原子轮换：先写新名再删旧名，真实名全程被治理、无裸露窗口
$G view --meta-dir /data/gfs alias --name pub2 --real team --retire pub
# rotated public name for real view 'team': 'pub' -> 'pub2' (gapless — 'team' stayed governed throughout, 'pub' no longer resolves)

③ fork（独立树：结构可写、内容只读、字节零复制）：目录项复制一份，字节经跨视图账本共享；在 fork 里删名字只摘自己的，基树分毫不动。

$G view --meta-dir /data/gfs fork --name lab --base team
# forked view 'lab' from base 'team': 5 entries, 2 shared object(s)
$G mount --view lab -m /mnt/lab --manager 127.0.0.1:50055 --roster-key-file /data/gfs/manager/roster.key &
# fork view 'lab' of base 'team': independent tree — structure writable, content read-only (EROFS)
mkdir /mnt/lab/docs/review                       # 结构操作放行
mv /mnt/lab/docs/2026/report.txt /mnt/lab/docs/review/   # 改名放行（只改 lab 自己的树）
ls /mnt/lab/docs                # 2026 note.md review
ls /mnt/lens/docs               # 2026 note.md   ← 基树没被回写：review 只存在于 lab
echo x > /mnt/lab/docs/new.md
# bash: Read-only file system   ← 内容写拒绝；自己 touch 出来的空文件同样写不进

④ graft（把基视图的选中条目接进 fork 的任意目录并逐条改名）：先 fork --empty 只建空树，再用计划文件（纯文本，源路径⇥目标名，目标名可省略）按需装入子集——字节依旧零复制。

$G view --meta-dir /data/gfs fork --name picks --base team --empty     # 只建根、不复制目录项
# forked view 'picks' from base 'team' as an EMPTY tree: root only, nothing copied
printf 'docs/2026/report.txt\t季度报告.txt\ndocs/note.md\n' > plan.tsv
$G view --meta-dir /data/gfs graft --name picks --src team --map plan.tsv
# grafted 3 entries (1 directory) from 'team' into 'picks' at /: 2 shared object(s), 0 skipped
# note: bytes were not copied — every grafted name holds the same object as its source; the object is freed only when no view names it anymore
# report.txt 接进根目录并改名为 季度报告.txt；note.md 原名接入；可加 --dest DIR 指定落点、--skip-existing 跳过同名

2.1.4 授权边界（三进程同机）

准入由服务端把关，不再是「挂载点权限就是全部」：mount 得先过 meta-server 与 data-server 两道门。同机起步常什么门都不开——这时任何能连上 127.0.0.1:50110 / 127.0.0.1:50100 的本地进程都能挂上任何视图，所以最小自觉是把 --listen 绑在回环地址上。OS 层还有一层：

chmod 750 /mnt/team                     # 用目录权限控制谁能进挂载点
sudo -u alice ls /mnt/team              # 以另一 OS 用户验证
需要逐调用方可撤销凭据、视图绑定、服务端强制只读、调用审计时，本机档一条命令就能开：token（1.2）+ --require-api-key（2.2.3），把那里的 10.0.0.5 换成 127.0.0.1 即可。这些能力从来不是「分布式档独有」，而是「服务端开没开门」——本机的门与集群的门是同一扇门。

2.1.5 配置文件：把引导也写进文件

每个旋钮的取值优先级恒为：命令行参数 > 环境变量 > 配置文件 > 内置默认值。grovefs 启动时自动加载一个 KEY=VALUE 配置文件填入尚未设置的变量：

# 查找顺序: $GROVEFS_CONFIG 指定路径 > $HOME/.config/grovefs/grovefs.conf
# 只认 GROVEFS_* 键；支持 # 注释、空行、可选 export 前缀、引号包裹的值
cat > ~/.config/grovefs/grovefs.conf <<'EOF'
GROVEFS_MANAGER=127.0.0.1:50055
GROVEFS_ROSTER_KEY_FILE=/data/gfs/manager/roster.key
GROVEFS_DEPLOYMENT=default
GROVEFS_HOME=/data/gfs
EOF

# 之前: $G mount --view team -m /mnt/team --manager 127.0.0.1:50055 --roster-key-file /data/gfs/manager/roster.key
# 之后: 只剩「这次挂哪个视图到哪儿」——引导由文件里的 manager 补齐，坐标仍从 roster 解析
$G mount --view team -m /mnt/team

注意：--view/-m 刻意不被收录——每次挂载都不同，写进默认值是错的。文件里有口令就 chmod 600。挂载的坐标只从 GROVEFS_MANAGER + GROVEFS_ROSTER_KEY_FILE（必要时配 GROVEFS_DEPLOYMENT）解析；GROVEFS_META_SERVER/GROVEFS_DATA_SERVERS 如今只被节点侧审计动词（du/gc）读取，不再驱动 mount。GROVEFS_HOME 只喂节点侧动词与两个服务（--home 的回退链是 --home → $GROVEFS_HOME → ~/.grovefs），写进文件也不会让挂载多出一种「本地形态」——挂载根本不看它。切多套环境用逐次 GROVEFS_CONFIG=~/gfs-B.conf $G …（每套一份文件），不要常驻 export——已导出的同名变量会静默压过配置文件。

2.2.1 起服务：先验后常驻

$G data-server --listen 0.0.0.0:50100 --data-dir /data/cluster --token "$TOK"

# 成功标志：各自打印一行 listening …；ss -lntp 里看到 50100/50110

验证通过后写 systemd 常驻。先建一份 root-only 的 env 文件（token 不进命令行，避免 ps 泄露），两个服务共用：

# /etc/systemd/system/grove-data-server.service

After=local-fs.target
[Service]

RestartSec=2

# /etc/systemd/system/grove-meta-server.service
[Unit]

After=local-fs.target
[Service]

Restart=on-failure
RestartSec=2
[Install]
WantedBy=multi-user.target
# /etc/systemd/system/grove-manager.service —— 挂载引导(§1.2):只在挂载那一刻被问一次,不在 IO 路径上;宕机不动活挂载,只让新挂载 fail-closed
[Unit]

2.2.2 建基视图（含存量数据零拷贝导入）

cat > seed.txt <<'EOF'

EOF
$G view --meta-dir /data/cluster create --view team --manifest ./seed.txt

$G import --view legacy --source /data/legacy --meta-dir /data/cluster --dry-run

2.2.3 授权：token + 逐调用方 API key

token 是集群准入的共享口令（1.2 已配）；但它是共享密钥——审计上分不出谁挂的，踢一个人只能轮换断全部。需要逐调用方凭据时启用 API key 体系：

# node1：铸造三把 key（--meta-dir 与 meta-server 同一路径；回显全文，库里同时留一份可逆副本）
$G apikey --meta-dir /data/cluster create --label node2-rw  --for mount --view team
$G apikey --meta-dir /data/cluster create --label node3-ro  --for mount --view team --ro
$G apikey --meta-dir /data/cluster create --label alice-key --for mount --view alice
# apikey created (a recoverable copy is now stored — `grovefs apikey secret --id …` reads it back):
#   id: aac1f51a…  label: node2-rw  scope: mount  view: team  rw: rw
#   key: aac1f51a…:32位hexsecret      # 新铸 key 统一 16 hex id + 32 hex secret（共 49 字符）；长格式 key 照样鉴得上

# 查看注册表：列表只给入库摘要的头尾指纹；盘上那份是 secret_enc 密文信封，
# 要拿回明文就 apikey secret --id（需 store key；本地直读不记审计，经治理口读才落账）
$G apikey --meta-dir /data/cluster list
# 按视图/label/owner/scope 过滤、轮换 secret、原地切读写/只读、撤销：
$G apikey --meta-dir /data/cluster list --view team
$G apikey --meta-dir /data/cluster list --label node --scope mount   # 子串匹配 label + 精确 scope，可叠加
$G apikey --meta-dir /data/cluster rotate --id aac1                   # secret 丢了：同一 id 重铸 secret，绑定/归属/审计全留（旧 secret 下次握手即拒）
$G apikey --meta-dir /data/cluster set-ro --id aac1 --rw      # 只读 key 热切回读写，活挂载 1s 内生效
$G apikey --meta-dir /data/cluster set-ro --id aac1            # 不带 --rw 即切回只读
$G apikey --meta-dir /data/cluster revoke --id 7c0e            # 撤销：活挂载在下一次服务端往返被封停、自卸载

开服务端门（两道都要开，且 fail-closed——先铸好 key 再上 flag，否则谁都进不来）：meta-server 加 --require-api-key；data-server 加 --require-api-key --meta-dir /data/cluster（读同一份 key 注册表）。客户端把 token 换成 key：

# node2（读写 key）
export GROVEFS_API_KEY='aac1f51a…:32位hexsecret'      # 走 env，不进 argv
$G mount --view team -m /mnt/team \
     --manager 10.0.0.5:50055 --deployment prod --roster-key-file /etc/grovefs/roster.key
# GROVEFS_API_KEY 已导出即生效，无需额外参数；也可显式 --api-key '<id>:<secret>'

# node3（只读 key）：写被服务端强制拒
mkdir /mnt/team/should_fail
# mkdir: cannot create directory ‘/mnt/team/should_fail’: Read-only file system

# 拿绑定 team 的 key 去挂 alice：绑定检查处即拒（比存在性检查更早）
# error: permission denied: this api key is bound to view 'team', not 'alice'

# node1：回读审计（每次连接含被拒的都落表）
$G apikey --meta-dir /data/cluster calls

systemd 客户端的对应改法见 2.2.5；systemd 挂载单元被撤销 key 的行为：挂载打印拒因后干净自卸载（退出码 0，Restart=on-failure 不会重拉——这是有意的收手不是崩溃）。

2.2.3· 数据面准入绑定：Data-Access Capability（防 rogue meta-server）

token 与 API key 都是入口门，认证“调用方能不能进门”，但不绑定“meta 面与 data 面是同一个可信服务端”。data-server 是扁平 KV、只认共享 token，于是握合法 token 的攻击者可自建恶意 meta-server、却把客户端指向诚实的 data-server，驱动其读写本不该碰的内容字节。闭合办法：给两服务配同一把共享 HMAC 密钥 K，客户端无需配置。

# 生成一把共享密钥（与 token 独立）
K=$(openssl rand -hex 32)
# node1：两服务同值 K（可写进同一份 root-only env）
$G meta-server --meta-dir /data/cluster --listen 0.0.0.0:50110 --token "$TOK" --data-access-key "$K"   # --data-access-ttl 0=永不过期（默认）
$G data-server --listen 0.0.0.0:50100 --data-dir /data/cluster --token "$TOK" --data-access-key "$K"
# 客户端照常挂，无任何新参数——能力在 M_OPEN/OP_OPEN 两次握手间自动流转
$G mount --view team -m /mnt/team --manager 10.0.0.5:50055 --deployment prod --roster-key-file /etc/grovefs/roster.key --token "$TOK"

效果：真 meta 在每次 M_OPEN 用 K 签一枚能力交给客户端，客户端在数据面 OP_OPEN 回放，开了 --data-access-key 的 data-server 用同一个 K 校验；rogue meta 没 K 签不出合法能力，其挂载即便持正确 token 也被拒（EACCES）。opt-in，不开则帧里无能力字段。诚实边界：它是“经真 meta 准入的证明”（通道绑定），不是 per-view ACL——能力不编码视图，“某调用方只能碰某棵视图”仍靠上面的 --view 绑定 key。详见 USAGE §6.1.1。

2.2.4 四种视图（服务端集中定义）

与 2.1.3 同一套命令，只是寻址换成 --meta-dir /data/cluster（在存储机上执行）；区别在分发面：定义存在服务端，客户机只需 mount --view <名>，不带任何本地规则文件。改定义热生效（≤2s，已挂载连接自动换形）。

# node1 上：定义一个只读透镜给外部协作者

# node2/node3 上：挂派生名，无需规则文件；M_OPEN 握手带只读标志

# 改规则热生效：替换 .layout 后，已挂载的派生连接 ≤2s 内换形，免重挂
printf 'only /docs\nhide /docs/internal\n' | tee /data/cluster/meta/views/docsonly.layout
# （或重新跑一条 view define 同名覆盖）

# 分发面差异一览（对照 2.1.3 的三进程同机形态）：
# ① docsonly → 客户机只给名；② pub → 全树可写，真名 team 同时不可直挂（服务端同拒）
# ③ lab → 结构可写/内容 EROFS；删名只影响 fork 自己；④ graft 接枝字节零复制

SQLite 档 view 操作的是服务端本地文件，所以要在 meta-server 所在机器执行；HA 部署下 meta/views/ 与整个 meta/_control/ 要手工同步到备机（PG 档无此负担，定义在共享库里——见 2.3.5）。

cat > ~/.config/grovefs/grovefs.conf <<'EOF'

$G mount --view alice -m /mnt/alice --ro # 本机只读叠加：同一引导，另一个视图

常驻挂载用模板单元（一个视图一个实例，%i = 视图名，挂载点固定 /mnt/%i；--foreground 保持附着，systemctl stop 自动 fusermount 干净卸载）：

# /etc/systemd/system/grove-mount@.service
[Unit]
Description=GroveFS mount view %i
After=network-online.target
Wants=network-online.target
[Service]
EnvironmentFile=/etc/grovefs/grovefs.env
ExecStartPre=-/usr/bin/fusermount -u /mnt/%i
ExecStart=/usr/local/bin/grovefs mount --view %i --foreground \
     --manager 10.0.0.5:50055 --deployment prod --roster-key-file /etc/grovefs/roster.key \
     --api-key ${GROVE_API_KEY} -m /mnt/%i
Restart=on-failure
RestartSec=2
[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl start grove-mount@team grove-mount@alice   # 一台机挂两个视图
findmnt -T /mnt/team      # 源显示 grovefs:team，FUSE 类型

两个注意：systemd 默认以 root 起挂载，上报 uid=0（可用 --run-as-uid N 指定属主槽位，仅进锁仲裁与审计）；其他用户要访问挂载点加 --o allow_other 并开 /etc/fuse.conf 的 user_allow_other。key 铸好后写进同一份 root-only env（密钥不进 ps 可见的 unit 文本）。

2.2.6 运维与验收

node2: echo x > /mnt/team/t.txt

node1: ls /data/cluster/blocks | head    # 256 个哈希桶子目录；对象按 key 命名，不是文件名

$G refs --meta-dir /data/cluster rebuild                          # 账本可疑时重建（只多留不少算）

# 单视图迁移：换机器、换系统（元数据 JSONL + 字节另行拷贝 blocks/）
$G view --meta-dir /data/cluster export --view alice --out alice.jsonl
$G view --meta-dir /data/cluster2 import --view alice --in alice.jsonl   # 目标机；--as-fork B 可恢复 fork 语义

# 数据服务重启对客户机透明：node1 拉起 data-server，客户机 IO 自动重连
# 干净卸载：systemctl stop grove-mount@team（或手工 $G umount -m /mnt/team）
八步验收全过（服务存活且监听、挂载带 grovefs 标签、跨机实时可见、锁跨机生效、字节在中心、数据服务重启自愈、卸载无残留、未知视图名拒挂且不建树）即认为部署合格。

2.3 PostgreSQL 分布式 · 命令演示

场景沿用 1.3：db1（10.0.0.9，PG16，max_connections=200）+ node1（10.0.0.5，存储机）+ node2/node3 客户机。客户机命令与 2.2 一字不差，本节只演示服务端差异与 PG 特有能力。

2.3.1 准备 PG（db1 上一次性）

sudo -u postgres psql -c "CREATE ROLE grove LOGIN PASSWORD '换成强口令';"
sudo -u postgres createdb grovefs
sudo -u postgres psql -d grovefs -c "GRANT CREATE,CONNECT ON DATABASE grovefs TO grove;"
# 只需 CREATE（建 schema/表）+ CONNECT：不需要 SUPERUSER，不需要预建任何表
# 第一棵树是在首个 view create 时开出的；pg_hba.conf 放行 node1 的网段即可

2.3.2 起服务：连接串不落 argv

# node1：连接串只放 root 可读文件（argv 在 ps 里全网可见）
sudo install -d -m 700 /etc/grovefs
sudo sh -c 'cat > /etc/grovefs/meta.env' <<'EOF'
GROVEFS_TOKEN=换成你的32字节随机串
GROVEFS_META_DIR=/data/cluster
GROVEFS_META_STORE=postgres://grove:pw@10.0.0.9:5432/grovefs
EOF
sudo chmod 600 /etc/grovefs/meta.env
# /etc/systemd/system/grovefs-meta.service —— 相比 SQLite 档只改 ExecStart 一行
[Unit]
Description=GroveFS meta-server (PostgreSQL backend)
After=network-online.target
Wants=network-online.target
[Service]
EnvironmentFile=/etc/grovefs/meta.env
ExecStart=/usr/local/bin/grovefs meta-server --listen 0.0.0.0:50110 \
          --meta-store ${GROVEFS_META_STORE} --token ${GROVEFS_TOKEN}
Restart=on-failure
RestartSec=2
[Install]
WantedBy=multi-user.target
# data-server 单元同 SQLite 档（字节路径不变）；它要开 key 门时读同一份 PG 控制面
# —— 把 GROVEFS_META_STORE 写进 data 的 env 文件即可（--meta-store 的 env 回退）
sudo systemctl daemon-reload && sudo systemctl enable --now grovefs-meta grovefs-data
journalctl -u grovefs-meta -n 20 --no-pager | grep -i 'store\|listen'
# meta-server listening on 0.0.0.0:50110 (store: postgres://…10.0.0.9:5432/grovefs)

GROVEFS_META_STORE 有双重身份：既是 systemd ${VAR} 展开的来源，也是 GroveFS 自己的 --meta-store env 回退（view/apikey/mcp/meta-server/data-server/du 未给 flag 时读它）——显式展开与省略参数取到同一份值。PG 下 meta-server 不需要 --meta-dir：权威树与控制面都在库里，服务端本地不落权威数据。

2.3.3 建基视图：一视图一个 schema

# node1 上：显式建 schema（挂载不会建；两种后端同一纪律）
$G view --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs create --view team

# 看 PG 里到底建了什么
sudo -u postgres psql -d grovefs -c '\dn'
#   grovefs_refs        ← 跨视图引用账本（共享表 grovefs_refs.holders）
#   grovefs_v_64656d6f  ← 视图 team 的 schema（名字 = grovefs_v_ + 视图名 UTF-8 字节的十六进制）
#   grovefs_control     ← 控制面（key/视图定义/放置表/审计）
sudo -u postgres psql -d grovefs -c '\dt grovefs_v_64656d6f.*'
#   node / ctrl / locks 三张表
两条硬规则：① 在 PG 后端上跑不带 --meta-store 的 view create 只会在本地造一个用不到的 <view>.db——治理命令必须带同一 --meta-store；② 视图名超过 25 字节会被拒（PG 标识符 63 字符上限，hex 编码翻倍；中文约 8 个字）。

2.3.4 授权：同一套 API key，落点在 PG 控制面

# 与 2.2.3 同一套命令，寻址换 --meta-store；key 与审计进 grovefs_control，本地不落 api_keys.db
$G apikey --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs \
     create --label node2-rw --for mount --view team
$G apikey --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs \
     create --label node3-ro --for mount --view team --ro
$G apikey --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs list
$G apikey --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs calls     # 审计回读

# 服务端开门与 2.2.3 相同（meta/data 两道 --require-api-key；fail-closed：先铸 key 再上 flag）
# 客户端挂载命令与 SQLite 档逐字相同 —— 线协议不变，客户机无感

PG 档的优势：带同一 --meta-store 可从任意可达节点治理（key/定义/审计都在共享库里），无本地文件要同步到备机；治理凭据可用 --for admin --owner 铸账号密钥，配 meta-server --control-listen 从管理机远程治理（不发数据库密码）。

2.3.5 四种视图：定义进 grovefs_control，其余语义不变

# node1 上：同一套 define/alias/fork/graft，寻址换 --meta-store
$G view --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs \
     define --name docsonly --base team --rules docsonly.rules
$G view --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs alias --name pub --real team
$G view --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs fork  --name lab --base team
$G view --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs graft --name lab --src team --map plan.tsv

# 验证：定义在库里（本地没有 .layout 文件）
sudo -u postgres psql -d grovefs -c "SELECT name, kind FROM grovefs_control.view_defs;"
# docsonly | derived   pub | alias   lab | fork

# 客户机：与 2.2.4 逐字相同 —— mount --view docsonly 只读、pub 全树可写、lab 结构可写内容 EROFS
# 改定义同样热生效（PG 看行的 xmin，≤2s 换形）

PG 档与 SQLite 档在视图家族上的两点差异：① 顶层 grovefs import（目录零拷贝登记）拒绝——它只能产出本地 SQLite 树，存量数据改走挂载点灌入（挂上视图后直接 cp/rsync）；② 就地扫本机 blocks/ 的离线 gc 同样拒绝，改走 2.3.7 的治理面形态。

2.3.6 多实例扩容与视图搬家（连接数封顶时）

每个活跃视图占 PG 档 12 条连接（8 写 + 4 读，--engine-idle-secs 300 默认回收空闲视图的连接，容量按「最近活跃视图数」计）。当活跃集仍要封顶 max_connections 时，扩容答案是多实例注册表 + 视图放置：把不同视图放到不同 PG 实例（一个视图的树永远只落在一个实例上），容量随实例数线性增长。示例：加入 db2（10.0.0.11，同规格 PG，max_connections=200），把热点视图 team1 挪过去。

# ① db2 装好库与账号（同 2.3.1）；② node1 上写实例注册表（每行 名字 = postgres://…，# 注释）
sudo sh -c 'cat > /etc/grovefs/instances.conf' <<'EOF'
# 第一条 = 控制面（放置表/key/定义都落在这里）
main  = postgres://grove:pw@10.0.0.9:5432/grovefs
team1 = postgres://grove:pw@10.0.0.11:5433/grovefs
EOF
sudo chmod 600 /etc/grovefs/instances.conf

# ③ 重启 meta-server：--meta-store 换成 file: 注册表；启动横幅报实例清单
# meta-server: 2 PG instance(s) [main, team1] — control plane on 'main'

# ④ 此后新视图自动向新机器均衡（选放置数最少的实例）；也可显式钉住
$G view --meta-store file:/etc/grovefs/instances.conf create --view team1 --pg-instance team1

# ⑤ 已存在的视图要搬家？view move 四步切换（snapshot → build → flip → retire）
$G view --meta-store file:/etc/grovefs/instances.conf move --view team1 --pg-instance team1
# 快照导出（挂载仍在写也不撕裂）→ 目标建副本并按行数自验（不触碰放置）
# → 改写放置行（唯一原子切换点，失败 DROP 副本回滚）→ 退役源 schema
# → 挂载客户端无感，字节不动，下次 M_OPEN 即路由到新家

要点与守卫：--keep-source 把源留作回滚点（反向 move 幂等复用副本，只切一次行）；视图挂载中拒绝搬家（先卸载）；alias/derived 拒绝（它们不拥有树）；fork 可以搬但基视图不跟随——搬完的 fork 与基视图分属两实例，后续这对的 graft 会被跨实例拒绝，搬家前想清楚。语义不变量：view list 跨实例合并、refs rebuild 逐实例重算后求和、gc 跨实例并集扫描。给集合加机器不影响已放置视图的落点（放置行说了算）。

2.3.7 运维与巡检（用 psql，不要用 sqlite3）

# 用量快数：du 的 PG 形态（字节来源仍是 data-server）
$G du --view team --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs \
     --data-servers 10.0.0.5:50100 --total

# 孤儿对象回收（PG 档）：meta-server 开治理口，gc 经治理面跨实例并集扫描
# meta-server 启动参数加: --control-listen 0.0.0.0:50130
$G gc --control-server 10.0.0.5:50130 --data-servers 10.0.0.5:50100           # 审计
$G gc --control-server 10.0.0.5:50130 --data-servers 10.0.0.5:50100 --apply   # 应用
$G refs --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs rebuild       # 账本重算（多实例逐实例求和）

# 巡检：schema 计数、连接占用、控制面放置表
sudo -u postgres psql -d grovefs -c "SELECT count(*) FROM information_schema.schemata WHERE schema_name LIKE 'grovefs_v_%';"
sudo -u postgres psql -d grovefs -c "SELECT count(*), state FROM pg_stat_activity GROUP BY state;"
$G view --meta-store file:/etc/grovefs/instances.conf list

# 备份与恢复：元数据随 pg_dump 迁移，本地只需另拷 blocks/
sudo -u postgres pg_dump -Fc grovefs > grovefs-$(date +%F).dump
sudo -u postgres pg_restore -d grovefs --clean grovefs-2026-11-16.dump
# 多实例部署逐实例各做一份；控制面实例那份同时覆盖放置表与控制面
# 高可用/PITR 交给 PG 自身（流复制）；--meta-store 与自研 HA 参数互斥，启动即 fail-fast

# 删基视图：一条命令（销账 + DROP SCHEMA 在同一事务，PG 的 DDL 是事务性的，无中间态）
$G view --meta-store postgres://grove:pw@10.0.0.9:5432/grovefs rm --name team --base --data-dir /data/cluster
验收：第一个挂载建立后 \dn 多出 grovefs_v_<hex>；ls /data/cluster/meta 里没有 team.db（权威树在 PG，不在文件里）；客户机读写与 2.2 的验收逐字相同。

2.4 网页管理台 · 账号、基视图授权与反代 TLS

示例环境：沿用 2.2 的 SQLite 部署（node1 = 10.0.0.5 持盘，data 50100 / meta 50110），给治理面留一个端口 50130；管理台网关与 nginx 同在 node1，网关只听 127.0.0.1:8787；运维从自己的工作站经 HTTPS 进入。PG 档（2.3）一字不差照抄——账号与授权只是换地方存（控制库里的表而不是 meta/_control/web_accounts.db），命令形状与页面能力完全相同。

管理台是一个独立子命令 grovefs web，而不是 meta-server 多开的一个网页入口：它是治理口前面的 HTTP 网关，自己不存账号、不存视图、不存审计，所以也不新增一套权限判定——“这个账号能碰哪棵树”仍然只在服务端一处。登录不产生能力，只限制并归属能力：一个会话只能以一个账号行动，每次调用以 account@ip 落审计。

2.4.1 一次性配置（node1，root）

第一个管理员只能由持有存储的进程放置：两面 flag 挂在 meta-server 上，且只在账号表为空时生效，所以 unit 文件反复读同一个 flag 的重启是幂等的，而换一个 --admin-user 会拒绝启动而不是悄悄多一个管理员。口令只有 --admin-password-file，没有 --admin-password（argv 对本机所有进程可见、会进 shell history；策略：至少 10 个字符，且不得等于账号名）。

sudo install -d -m 700 /etc/grovefs
# ① 安装期管理员的口令（只在表空时被读一次；事后改这个文件不会改任何口令）
sudo sh -c 'umask 077; printf "%s\n" "RootOps-pw-2026" > /etc/grovefs/web-owner.pw'
# ② 网关要一把 admin scope 的账号密钥（§2.2.3 那套 apikey，回显一次且事后可读回）
sudo sh -c 'umask 077' ; $G apikey --meta-dir /data/cluster create --label web-console --for admin --owner rootops
sudo sh -c 'umask 077; printf "%s\n" "刚打出来的 id:secret" > /etc/grovefs/control.key'
# ③ meta-server 的 ExecStart 追加三面 flag（治理口 + 安装期管理员）：
#    --control-listen 127.0.0.1:50130 --admin-user rootops --admin-password-file /etc/grovefs/web-owner.pw
sudo systemctl restart grovefs-meta
# 横幅多出两行：created the first web account 'rootops' (role admin) from the install-time flags …
# 与  web console sign-ins are verified HERE (`grovefs web --control-server 127.0.0.1:50130`) …

2.4.2 第三个服务与反代 TLS

网关只说明文 HTTP，所以默认绑 loopback；绑可路由地址会直接拒绝启动。TLS 终止交给前置反代，并给网关加 --use-x-forwarded-for，否则登录限速与审计里的 IP 全是反代自己的。

# /etc/systemd/system/grove-web.service
[Unit]
Description=GroveFS management console
After=grovefs-meta.service
Requires=grovefs-meta.service
[Service]
ExecStart=/usr/local/bin/grovefs web --control-server 127.0.0.1:50130 --api-key-file /etc/grovefs/control.key --listen 127.0.0.1:8787 --use-x-forwarded-for
Restart=on-failure
RestartSec=2
[Install]
WantedBy=multi-user.target
# /etc/nginx/sites-available/grovefs-console —— TLS 在这里终止
server {
    listen 443 ssl http2;
    server_name gfs-console.internal;
    ssl_certificate     /etc/letsencrypt/live/gfs-console.internal/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/gfs-console.internal/privkey.pem;
    add_header Strict-Transport-Security "max-age=31536000" always;
    location / {
        proxy_pass http://127.0.0.1:8787;
        proxy_set_header Host $host;                    # 别改写它：网关校 Origin 的主机部分 == Host
        proxy_set_header X-Forwarded-For $remote_addr;  # 于是限速与审计里是真实客户端
    }
}
server { listen 80; server_name gfs-console.internal; return 301 https://$host$request_uri; }
sudo systemctl daemon-reload
sudo systemctl enable --now grove-web nginx
# 只对内网开 443；8787 与 50130 不对外（开了 --use-x-forwarded-for 就要确保只有反代能连 8787）
# 没反代也不想开端口时，一条 SSH 隧道就够：ssh -L 8787:127.0.0.1:8787 node1

2.4.3 建号、划基视图、撤权（headless与页面同效）

建号只给人一个身份，grant add 才是划地方；授权的对象是基视图——此后这棵树下新长出的 fork、改的别名、加的透镜与绑到这些名字上的密钥全部自动在范围内，不必逐名追加。下面的命令在持盘主机跑；给了 --control-server + --api-key-file 就任意机器可跑（§2.2.3）。

$G web --control-server 127.0.0.1:50130 --api-key-file /etc/grovefs/control.key \
   account create --account bob --password-file ./bob.pw
# web account created: bob
#   role:  user
#   bases: none — it can sign in and govern nothing yet
$G web --control-server 127.0.0.1:50130 --api-key-file /etc/grovefs/control.key \
   grant add --account bob --base team
# bob now governs 'team' and everything derived from it, as granted by rootops.
# That covers its forks, aliases and lenses, and the keys bound to any of those names.
$G web --control-server 127.0.0.1:50130 --api-key-file /etc/grovefs/control.key account list
$G web --control-server 127.0.0.1:50130 --api-key-file /etc/grovefs/control.key grant list

# 撤权不必等会话过期：服务端每请求重读主体，下一个调用就撞墙
$G web --control-server 127.0.0.1:50130 --api-key-file /etc/grovefs/control.key \
   grant rm --account bob --base team
# bob no longer governs 'team'.

# 停人用 disable（可逆、授权原样保留），删号用 account rm
# ⚠ account rm 不撤销该号铸过的 api key——否则一个删号会静默停掉一个在跑的生产挂载
$G web --control-server 127.0.0.1:50130 --api-key-file /etc/grovefs/control.key account disable --account bob

审计台账的保留期是部署要自己决定的那件事：控制台每一点、每个治理调用、每次挂载握手都在控制面库里落一行（PG 档 grovefs_control.mcp_calls，SQLite 档 meta/_control/api_keys.db），而开着控制口的服务端默认带 7d 窗口（把 --audit-retention never 说出口才是全部保留）。两条路：给 meta-server 追加 --audit-retention 365d（必须与 --control-listen 同时给；后台按窗口 1/24（5min..1h）扫、开机先扫一刀再睡），或把它当成例行巡检——先 $G apikey --control-server 127.0.0.1:50130 --api-key-file /etc/grovefs/control.key purge --before 365d --dry-run 数一下会掉多少行，确认后再去掉 --dry-run。控制台里没有这个按钮，也不是漏了：purge 是 SUPERUSER 动词，被这张表记录的账号不该是有权修剪它的人；表现在多大，审计页顶部那句话会直接讲出来。

四件容易做错的事：① 降级或删除唯一在职的 admin 会被拒——先建第二个 admin 并验证能登进去再动第一个；② account passwd 不踢掉已开的会话（那是网关的会话表），要立即停人是 disable；③ 口令只能从 --password-file / --password-stdin 进去，两者互斥且不存在 --password；④ 页面能点的动词是写死的 32 个白名单，gc.scan、gc.apply、refs rebuild、view rm --base、fork graft 五个保留在 CLI——它们的 dry-run 报告与逐步确认是调用的一部分，想跑这些就回到 §2.2.6 / §2.3.7。
验收：浏览器打开 https://gfs-console.internal/ 能看到登录页；拿 rootops 登录→总览页把八个部署数排成每行 4 个、共两行的统计卡（过期密钥非零时那张转琥珀色），卡下方的「本部署」事实表报出后端+describe 行、元数据根、服务端角色、命名空间（基视图/定义拆开）、凭据（live/expired 拆开）、账号数与活动量；拿 bob 登录→视图页只列 team 一棵，选中一棵基视图时右侧多出它的谱系面板（它的别名/透镜/fork 与逐层向下的子名字），能建 fork、能在密钥页给自己那棵铸一把 mount key 并就地改它的备注与有效期，而“Accounts”页只剩“改自己的口令”；故意输错口令五次→第六次回 429 带 retryAfter；审计页里每一行都带 account=<人>@<ip>，并能按时间窗、平面、事件类型、成败与关键字五个维度检索。五页共用同一套设计系统（字号阶梯与间距令牌、卡片化面板、抽屉与可折叠详情），文案全部过词典、中/英一键切换；密钥页的 key 列是入库的头尾指纹而非明文，这条取舍写在页面上；把某把 key 的副本读回只在属主（或超级账号）那里成功，跨账号被拒。端到端断言见 web 套件（183 条）。
