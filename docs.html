GroveFS 使用说明

一种用户视图 FUSE 文件系统:物理数据集中存放在硬盘,不同用户挂载各自看到独立的文件列表,列表支持自定义文件夹层级,彻底脱离 NFS。

语言 Rust FUSE fuser 0.18 多线程 元数据 SQLite(rusqlite bundled) 或 PostgreSQL(--store postgres://…) 传输 自定义 TCP 帧(非 NFS/gRPC) 全板 GREEN 26 套件(build+unit+posix+edge+e2e+remote+errors+resilience+concurrent+metasrv+ha+striping+locks+freshness+disp_fresh+acl+layout+import+govcheck+govtime+grovesci+mcp+apikey+pg+pg_parallel+bench)

1是什么 / 核心概念

一句话:把「谁能看到什么(视图)」和「数据实际存在哪(对象)」彻底分开。每个用户一棵独立目录树,互不可见;字节统一存在物理块目录里。

视图 view

每个用户一棵独立目录树(含自定义层级),存在一个 SQLite 库:<home>/meta/<view>.db。不同用户互不可见。

数据对象 object

文件的真实字节。一个文件 = blocks/ 下一个以 UUID 命名的对象(或条带化的多个分块)。视图目录项指向对象 key。

基目录 --home

同时容纳 blocks/(数据)和 meta/(视图)的物理根。默认 $GROVEFS_HOME 或 ~/.grovefs。meta-server 用子命令自己的 --db-path 指元数据根(视图库在 <db-path>/meta/),语义更明确。

关键:视图与数据天然分离。视图只是「目录树 + 指针」,字节永远在 blocks/。这正是"不同用户挂载显示不同列表、数据都在硬盘上"的实现基础。
--view 与路径容量:--view 是视图命名空间的任意标签,与 Linux 用户名无关——不调 getpwnam、不校验 uid、不要求 useradd。alice、team-a、u42、研究组 都可用,只用作 ① <home>/meta/<view>.db 库文件名 ② FUSE mount 上的 grovefs:<view> 标签。鉴权 = 能访问 --home/blocks/ + 可选 --token,不来自 Linux 用户身份。一个用户一棵树,树内可 mkdir/touch 任意多个文件与目录、任意深度,与自家 home 无差异;跨用户隔离的粒度是「整棵视图树」而不是单个路径。--manifest 只是骨架预建入口,不是路径数量上限。

2架构与原理

三层解耦,全走 trait 抽象:

┌─ FUSE 挂载进程  fs_impl.rs:GroveFS(&self, 多线程安全)
│    ├── MetaProvider trait  视图树访问(12 方法)
│    │     ├── 本地:  MetaEngine  → <home>/meta/<view>.db
│    │     └── 远程:  RemoteMeta  → meta-server(中心权威)
│    └── StorageBackend trait 数据对象 IO
│          ├── 本地:  LocalBackend → <home>/blocks/<key>
│          ├── 远程:  RemoteBackend → data-server
│          └── 条带:  ShardedBackend → 多 data-server
└─ 传输:自定义二进制帧 over TCP(定长头+变长体),连接池并发

为什么这样设计

  • trait 接缝可插拔:本地/远程/条带对上层透明,切换只是换个实现。
  • 中心 MetaServer:同一用户在多客户机共享一份权威视图,不再各存各的副本导致分叉。
  • 事件总线 + Notifier:写成功后向订阅者推送失效,解决"默认缓存下内容新鲜度"。
  • fuser 0.18 多线程:每线程独立 /dev/fuse fd(clone_fd),请求并发派发不串行。
  • 元数据读并行 + 目录分页 + READDIRPLUS:每个视图的存储引擎除单条写连接外再开 4 条只读连接(SQL READ_POOL_SIZE、PG PG_READ_POOL_SIZE)服务 lookup/getattr/readdir,读不再排在写锁后面(SQLite 写仍串行在同一权威连接上;PG 写走 SERIALIZABLE 写池并行,见 §6.2),服务端引擎同样吃各自后端的池;目录列举按 readdir_page 下推成 SQL LIMIT/OFFSET、回复缓冲按 32→1024 几何块填充,一个内核请求付 O(缓冲) 而非 O(整棵目录);默认协商 FUSE_DO_READDIRPLUS(内核 ≥4.6)让属性随目录项一次带回。同一份 5001 条目录、同一挂载点、每趟新挂载实测 ls -l:2.56s(只留分页 5.22s;改造前基线 55.34s,三份输出排序后逐字节相同)。分页与 PLUS 在所有能自身分页的 provider 上启用——本地 SQLite/PG,以及对接 SQLite/PG meta-server 的远端挂载(新 M_READDIRP 帧把 offset/limit 下推到服务端):同一 5001 条目录经 meta-server+data-server 实测由改造前 ~54s → 2.29s(只关 PLUS 保留分页 4.22s,两份输出逐字节相同)。仅派生/透镜视图与不含该能力位的老服务端仍走每缓冲一次全量列表、不协商 PLUS。

一次写请求的完整路径（数据面 / 元数据面各走一半）

app write()/close()
   ├─ 数据面   → RemoteBackend ─TCP帧→ data-server → blocks/<key>（UUID、扁平存）
   │                                    ≥4MiB 分片并发；大文件跨多 data-server 条带
   └─ 元数据面 → RemoteMeta   ─TCP帧→ meta-server → 权威视图树（默认 SQLite，或 PostgreSQL）
          create / rename / setattr / touch_mtime …
          └─ 写成功 → 事件总线推 inval_entry+inval_inode → 对端下次访问即时可见
  • 谁持有权威：meta-server 是单一权威串行点——同一 view 的一棵树只由这一个进程落到存储引擎（SQLite 一 view 一 .db，PG 一 view 一 schema），所有客户端经 TCP 帧汇聚到它。有意为之（杜绝各存副本导致的视图分叉），不是疏漏。
  • 客户端从不直接碰存储：既不开 .db 文件、也不持 PG 连接串，只说 GroveFS 线协议；后端是 SQLite 还是 PG 对客户端完全透明、命令一字不变。

3快速上手(单机本地模式)

数据和视图都在本机同一个 --home,无需任何 server,先体验功能最快。

Y=./target/release/grove
BASE=/data/myfs                       # 物理基目录

# 1) 初始化两个用户的视图
$Y --home $BASE init --view alice
$Y --home $BASE init --view bob

# 2) 挂载(前台运行,Ctrl-C 即卸载;或加 & 后台)
$Y --home $BASE mount --view alice --mountpoint /mnt/alice
$Y --home $BASE mount --view bob   --mountpoint /mnt/bob     # 另一终端

# 3) 像普通目录一样读写、建自定义层级
mkdir -p /mnt/alice/projects/2026
echo "年度报告" > /mnt/alice/projects/2026/报告.txt
ls /mnt/bob                                      # bob 看不到 alice 的文件

# 4) 卸载
$Y umount --mountpoint /mnt/alice
视图隔离:/mnt/alice 与 /mnt/bob 是两棵独立的树,互不可见;层级(mkdir 嵌套目录)完全自定义。

4用 manifest 预建自定义层级

init --manifest 在建视图时一次性铺好目录骨架。每行仅两种指令:mkdir <path> 或 touch <path>,行首 # 为注释。

# seed.txt
mkdir projects
mkdir projects/2026
touch projects/2026/README.txt
$Y --home $BASE init --view alice --manifest ./seed.txt
# 输出:applied seed manifest ./seed.txt

挂载后即见预建层级;重复 mkdir/touch 幂等,不报错。

5生产拓扑:中心存储 + 多客户机 LAN 挂载

真实场景:数据放中心集群,多台客户机经 LAN 挂载,同一用户跨机器看到同一份权威视图。拆成两个服务:

# ===== 中心节点 =====
$Y data-server --listen 0.0.0.0:50100 --root /data/cluster
$Y meta-server --db-path /data/cluster --listen 0.0.0.0:50110

# ===== 每台客户机(远程挂载不需要 --home,本地什么都不落) =====
$Y mount --view alice \
     --data 10.0.0.5:50100 --meta 10.0.0.5:50110 -m /mnt/alice
选项作用
--data host:port文件 IO 走网络到 data-server,不碰客户机本地盘(非 NFS)。
--meta host:port视图由中心 meta-server 提供 → 多客户机挂同一用户 = 共享同一棵权威树。
--data a,b,c逗号分隔多地址 → 启用跨 server 确定性条带(见 §8.2)。
--meta 主,备故障转移列表,主挂自动切备(见 §9)。

客户机本地不留视图副本、也不落盘：给了 --data/--meta 的远程挂载不需要 --home（传了也不写任何东西）——字节直连 data-server，视图树直连 meta-server，ACL 鉴权全部在服务端。

6共享视图与权限模型

GroveFS 的权限栈只有两层——令牌 = 集群准入，view 名 = 树选择。--view 字符串本身不是身份：任何 uid 只要挂同一个 --meta <addr> + --view alice 都会落到 alice 的同一棵权威树上，看到彼此写入。这是有意的，也让“多人共享一个视图”开箱即用。

一图看懂：客户端(viewer) → 门控 → view → 存储

隔离单位是 view 名，不是客户端——N 个客户端 ↔ M 个 view（多对多），
view_acl(<db-path>/meta/acl.db) 只决定“哪个 uid 准挂哪个 view”

客户端 A · uid=1000   mount --view alice ─┐
客户端 B · uid=2000   mount --view alice ─┤ 同一个 --view → 落进同一棵树；一个客户端也可
客户端 C · uid=1000   mount --view bob    ─┘ 同时挂多个 view（多对多）
        │
        ▼  TCP 帧 M_OPEN(view, token, uid)   客户端从不开 db 文件 / 不持 PG 连接串
┌─ meta-server（单一权威写者）—— 按序过门，再路由
│   ① token 校验   不匹配 → E_AUTH（集群准入，唯一确定性门；uid 自报属 advisory）
│   ② 读门 view_acl  无行 = 无约束；有任意行 = 白名单，需 can_read，否则 E_AUTH 拒挂载
│   ③ 写门           每个写意图 op 逐次重查 can_write，否则 E_NOTPERM（FUSE 侧落 EPERM；不缓存 → revoke 即时生效）
│   ④ view 名 → 引擎缓存  首次 M_OPEN 懒开，之后同 view 命中同一实例
└──┬──────────────────────────────────────────
   ▼ view=alice                        ▼ view=bob
  alice 权威树（A、B 共享，写串行化）    bob 权威树（仅 C，与 alice 互不可见）
   ├── SQLite（默认）： 一 view = 一个独立 db 文件  <db-path>/meta/alice.db · bob.db
   └── PostgreSQL（--store）：一 view = 一个独立 schema grovefs_v_616c696365 · grovefs_v_626f62

结论：数据库里独立存储的单位是「视图」而非「每个客户端」；alice 的树不管被几台机器挂都只有这一份。
数据面与视图树解耦：文件字节走 data-server → 存进其 --root 下的 blocks/<key>，树里只存 data_ref 引用。
常见疑问：多机 LAN 共享一棵树需要 PG 吗？——不需要。共享能力来自「同一个 meta-server + 同一个 --view」，与底层是 SQLite 还是 PG 无关；默认 embedded SQLite（零外部依赖）就支撑多客户端挂载、写串行化、实时失效推送，已由 metasrv/freshness/locks 套件在纯 SQLite 上证明。PG 只在服务端（meta-server 经 --store postgres://… 连接，客户端无此选项、不感知），价值是把持久化/HA/备份/PITR 交给成熟数据库。写并行（PG 独有，opt-in）：默认 SQLite 后端对同一 view 是单写者（一条权威连接 + 互斥锁，写串行）；换 --store postgres://… 后写路径放宽为至多 8 连接的 SERIALIZABLE 写池（HopsFS 路线，事务基座交给 PostgreSQL 自带 SSI），不相交行上的并发写真正并行提交、冲突侧透明重试（详见 §6.2）。故多机共享一棵树仍不需要 PG，PG 的增量价值是元数据写并行 + 持久化/复制/PITR 成熟度。

6.1 多人共享同一 view

多台机器、不同 OS 用户，都 mount --view alice --meta … --data … → 元数据经 meta-server 集中（一棵 SQLite/PG 树，串行化写）、内容经 data-server 集中（一份 blocks/）；ls 或 cat 立刻跨端可见，实时失效推送保证收敛。若需在同一棵共享树里区分职责（例如只读审阅者），在中心元数据根上开白名单（acl 自带 --db-path，与 meta-server 的 --db-path 同名同目录，两者读的都是 <db-path>/meta/acl.db；PG 模式下两者改读同一实例的共享表 grovefs_acl.view_acl，acl 须带与 meta-server 同款 --store URI）：

# rw 协作者 uid=1000
$Y acl --db-path /data/cluster allow   --view alice --uid 1000 --read --write
# 只读订阅者 uid=2000
$Y acl --db-path /data/cluster allow   --view alice --uid 2000 --read
$Y acl --db-path /data/cluster list    --view alice          # 查看已授权 uid
$Y acl --db-path /data/cluster revoke  --view alice --uid 2000   # 撤销行

存储位于 <db-path>/meta/acl.db（即 meta-server 同一元数据根下的 meta/；PG 模式下改存同一 PG 实例的共享表 grovefs_acl.view_acl，grove acl 须带同款 --store URI，见 §6.2），单表 view_acl(view, uid, can_read, can_write, PRIMARY KEY(view, uid))。查询为单条 (NOT EXISTS …) OR EXISTS (… AND can_read=1) 谓词，任何 DB 错误一律 fail-closed（归 false，绝不因库错而误放行）。语义：无行 = 无约束（任何 uid 挂同一 view 都放行，向后兼容旧行为）；有任意行 = 白名单（无匹配行→ M_OPEN E_AUTH 拒挂载、挂载 fail-fast；仅 read 授权→ 写意图 op 前逐 op 动态重查、回 E_NOTPERM（客户端 FUSE 侧落 EPERM，区别于 HA 备机 E_ROFS 故障转移信号），读仍放行）。写门不在 M_OPEN 缓存，故 acl revoke/降级对已建立连接即时生效。本地模式（无 --meta）同样走读门校验；写门落本地 SQLite 文件，同 uid 无法强制隔离，依赖 OS 文件权限。客户端上报 uid 默认 geteuid()，可 mount --as-uid N 显式覆盖，用于共享 meta-server 上按角色挂载。

诚实边界：TCP 客户端自报 uid 属 advisory（客户端可伪造），真正的准入仍由 --token 把关；白名单适合“已通过 token 准入的集群内部职责分离”，不适合防内鬼。另两个行为边界：① 加锁类 op（flock/F_SETLK，含锁续约）归为写意图（要写中心 locks 表），只读授权对它们一律 EPERM，只读角色需共享锁就得给 --write；② 读门只在挂载（M_OPEN）时校验一次，“revoke 即时生效”仅指写门（逐 op 重查），撤读后已建立连接会读到重挂为止。由 test_acl.sh 22 个断言证明（无行时任何 uid 放行、有行后未授权 E_AUTH、read-only 写回 EPERM、revoke 后门重新打开、本地 --as-uid 同名拦截、以及 §5b TOCTOU 回归：就地 rw→ro 降级后存活挂载即时拒写、读仍放行 …）。

6.2 元数据后端可切换：SQLite ↔ PostgreSQL

仅指 meta-server 的权威存储；客户端看到的线协议不变。默认 embedded SQLite（一 view 一 <home>/meta/<view>.db）；可切为 PostgreSQL：

# 默认（SQLite）
$Y meta-server --db-path /data/cluster --listen 0.0.0.0:50110

# PostgreSQL：一 view 一个 schema grovefs_v_<hex(view)>，事务化 rename/unlink/lock
$Y meta-server --db-path /data/cluster --listen 0.0.0.0:50110 \\
     --store postgres://user:pw@10.0.0.9:5432/grovefs

# 客户端命令完全一致（仍 --meta host:port --view alice）
$Y mount --view alice \\
     --data 10.0.0.5:50100 --meta 10.0.0.5:50110 -m /mnt/alice
  • PG 模式与自研 HA 互斥：--store postgres://… + 任一 --role standby / --peer / --witness 在启动时直接 fail-fast（VACUUM INTO 快照复制是 SQLite 特性）；PG 上 HA 请交给 PostgreSQL 自己的流复制 / logical replication / PITR——那本来就是比文件级快照更强的机制。
  • ACL 白名单随元数据面同迁：SQLite 模式下落 <db-path>/meta/acl.db；PG 模式下改存同一 PG 实例里的共享表 grovefs_acl.view_acl（meta-server 的门控与 grove acl --store 读的都是它）——整条元数据面（树 + 锁 + ACL）收进一个库，一次 pg_dump 即全量备份；此时 <db-path> 只剩派生视图定义等配置文件，不再持 acl.db。
  • 建表由服务端在 view 首次 M_OPEN 时幂等 CREATE SCHEMA IF NOT EXISTS + CREATE TABLE IF NOT EXISTS 完成，不需要预迁移脚本；根节点固定 id=1，setval(pg_get_serial_sequence(...), MAX(id)) 对齐序列，ROOT_INO 语义与 SQLite 完全一致。
  • 写并行（PG 独有，opt-in）：默认 SQLite 后端对同一 view 是单写者（一条权威连接 + 互斥锁）；换 --store postgres://… 后写路径改为至多 PG_WRITE_POOL_SIZE = 8 连接的 SERIALIZABLE 写连接池（HopsFS 路线，事务基座交给 PostgreSQL 自带 SSI）：不相交 (parent_id, name) 行上的并发写真正并行提交，读写重叠的一例由 SSI 中止并透明重试（200µs–25ms 指数退避、SERIALIZATION_MAX_ATTEMPTS = 12），SQLSTATE 40001/40P01 绝不外泄给 POSIX 调用方；rename 的环检查读、unlink 的引用计数 GC 读都并回同一事务。这是把「单权威写者」放宽为「单权威调度（serially equivalent）」，I1–I4 在任意 SSI 接受的调度下逐条不变。
  • 为什么没做 Redis：Redis 的 K/V+TTL 模型与视图树（rename/unlink/hardlink/refcount GC 需事务、锁需行级仲裁）不同构——把 relational 语义硬塞进 Redis 等于在应用层重做一个 PG，收益为负。GroveFS 只加 PG，不加 Redis。
由 test_pg.sh 19 个断言证明（拒绝 PG+HA 组合、单客户端 CRUD/rename/hardlink/symlink、docker exec psql 直接数 grovefs_v_<hex> 行数、跨客户端 mount A/B 收敛、hardlink unlink 跨端可见）；写并行另由 pg_ssi Rust 套件（5 项：distinct-parents 并行、同名竞争唯一胜出、并发 rename、hardlink 双名并发 unlink 仅一次 GC、混合 create+rename 收敛）与 pg_parallel bash 套件（三挂载 45 并发 create 墙钟远低于串行等效、同名并发 mkdir 恰一次成功且 node 表恰一行、无序列化错误外泄）端到端证明；无 PG 主机上均自动 SKIP，不拉低 GREEN。

8如何处理数据(重点)

8.1 物理布局

  • 单对象:blocks/<key>,一文件=一对象文件,扁平存放(不用深层目录,避免 inode/目录项膨胀)。
  • key 命名:写入时生成 UUID 作对象 key,存进视图 data_ref 字段。
  • 条带编码:data_ref = s<N>:<stripe_bytes>:<uuid>,第 i 块 key = {uuid}#{i},落在 servers[i % N]。无 s 前缀 = 旧单对象,天然向后兼容。

8.2 多 data-server 条带(聚合容量/带宽)

$Y mount --view alice \
     --data 10.0.0.5:50100,10.0.0.6:50100 --meta 10.0.0.5:50110 -m /mnt/alice
  • 文件 ≥ 16 MiB 才分块;小文件自然只落 chunk0(单节点)。
  • 条带读写内部复用分块并行 IO 原语。
  • 单地址 --data host:port 与旧行为完全一致。
诚实:条带的价值是把大文件摊到多节点的聚合容量。单条已饱和链路(loopback/单网卡)上实测无吞吐增益,须真独立链路才能测出收益——无实测数字不声称收益。

8.3 删除 / GC

unlink 后视图解除引用,后端据 key 尽力删全部分块;条带 remove 展开删所有 chunk,幂等(残留块可被 GC 清)。

8.4 备份与迁移

  • 数据对象:blocks/ 就是普通文件目录,可直接 rsync/文件系统快照备份。
  • 视图库:SQLite——本地模式 <home>/meta/<view>.db,meta-server 则在其 <db-path>/meta/ 下。勿在有写活动时裸拷 DB 文件;单机先停写或 checkpoint 后再拷,HA 模式由 meta-server 用备份 API 复制(见 §9)。PG 后端时 backup_to_bytes 有意返回错误,交给 PG 自己的流复制/PITR。

9高可用:meta-server 主备

# 主:读写,并把快照周期推送给备
$Y meta-server --db-path /data/nodeA --listen 10.0.0.5:50110 --role primary --peer 10.0.0.6:50111
# 备:只读服务,主心跳丢失后自动提升为 primary
$Y meta-server --db-path /data/nodeB --listen 10.0.0.6:50111 --role standby --peer 10.0.0.5:50110
# 主(可选 RPO=0):加 --sync-repl,写返回前同步等备落盘 ACK
$Y meta-server --db-path /data/nodeA --listen 10.0.0.5:50110 --role primary --peer 10.0.0.6:50111 --sync-repl
# 真 fencing(opt-in):加 --witness <逗号分隔的 data-server 仲裁者列表,推荐奇数 N>,多数派授权把双写窗口收敛为有界(fail-safe)
$Y meta-server --db-path /data/nodeA --listen 10.0.0.5:50110 --role primary --peer 10.0.0.6:50111 --witness 10.0.0.7:50100,10.0.0.8:50100,10.0.0.9:50100
# 客户端故障转移列表:主挂自动切备继续读写
$Y mount --view alice \
     --meta 10.0.0.5:50110,10.0.0.6:50111 --data 10.0.0.5:50100 -m /mnt/alice
  • 两节点必须用各自独立的 --db-path(各存一份视图副本,节点间靠快照复制)。
  • primary 每 ~500ms 推快照 + 心跳 epoch;standby 心跳超时后提升并 epoch+1,旧主恢复发现更高 epoch 自动降级。
  • --sync-repl(opt-in,默认关闭):写 op 返回客户端前同步推快照并等备 fsync + 原子 rename 的 ACK,把 RPO 从 ~500ms 降到 0;代价为多一个控制通道 RTT + 一次 VACUUM INTO fsync。备不可达/超时时诚实降级为 async 并打 warn(不谎报 0)。由 test_ha.sh 段 7(RPO=0)/段 8(分区降级)证明。
  • --witness <addr[,addr...]>(opt-in,默认关闭):用主备都能访问的一个或多个共享 data-server 作独立仲裁者集合(逗号分隔,推荐奇数 N;N=1 即退化为单仲裁、行为与旧版完全一致)。权威需严格多数派 quorum_size(N)=N/2+1 个仲裁者同时授予——每个仲裁者都是下述相同的 Fence 租约节点,meta 侧对全列表并发 fan-out 并按多数派判决(witness_quorum)。多数派交叠保证正确:两个多数派集合必交于≥一个仲裁者,该仲裁者只把 token 顶高给第一个 claimer(第二个见 prev==我 只算续约不算顶高),故同值碰撞天然只有一主。每个仲裁者维护单调 fence token(OP_FENCE 的 fetch_max CAS 回传折入前的值 prev):claim 赢当且仅当 prev < 我的 epoch,prev >= 我 则被 fence(对端胜出或同值碰撞)——用 prev 而非折后 max 正是为了在仲裁者恢复时区分同值碰撞、绝不双主。在任 primary 每 tick 向多数派 续一份有界租约(lease,默认 3s)(多数报 prev>我则自降级);每个仲裁者拒绝重叠租约——同一时刻至多一份活租约,故多数活租约本身即独占权威的证明,写请求由本地租约有效性直接放行(不再每写一个仲裁 RTT,仅每续租一次,摊薄到整个窗口),被 fence 的过期主在租约到点后的下一次复证即拒绝;提升方亦非重叠——须待前任租约到期才可抢占(prev>=candidate 同值碰撞/对端更高,或前任租约尚活,则拒绝/延后,旧主可证明地已停)。数据面同遭门控:元数据面复证拦不住内容字节(write() 先落 backend、再 debounced touch meta),故客户端把其实时 epoch 贴到每个写意图数据帧(create/write/truncate/remove/fsync),作为 witness 的 data-server 对 epoch < token 的帧直接回 EROFS,过期主无法绕过元数据面静默写入内容;被封帧会向权威重取 epoch 并自动重试一次(自愈)。更关键的是 data-server 把「epoch 校验 + 落盘」与「仲裁 claim」用读写锁线性化(claim 取独占会等在途写排空),而 witness 与存储同在一节点,故过期写的字节不可能与新主写交叠——内容撕裂写在仲裁节点上被真正闭合(不再是“有界窗口”)。部署前提:该数据面门控只对被 quorum 顶高过 token 的 data-server(即 --witness 列表内的节点)生效,故须把 witness 与客户端实际写入的内容盘同节点部署;若内容盘在 witness 集合之外,它的 token 恒为 0、数据面 gate 不生效,仅剩元数据面 fence 兜底(不会双主,但少了内容层的第二道防线)。部署前提:该数据面门控只对被 quorum 顶高过 token 的 data-server(即 --witness 列表内的节点)生效,故应将 witness 与客户端实际写入的内容盘同节点部署;若内容盘在 witness 集合之外,它的 token 恒为 0、数据面 gate 不生效,仅剩元数据面 fence 兜底(不会双主,但少了内容层的第二道防线)。FAIL-SAFE:配置了 witness 却组不到租约多数派连续 >宽限(3s)时,节点放弃写权限——primary 自降级、standby 拒绝提升(写冻结,宁牺牲可用也不冒双写;瞬时仲裁错误不误伤单写,持续故障才由宽限兼底)。相比单仲裁的可用性提升:宕掉少数仲裁者仍能组多数续租、不冻结写,且少数仲裁者的 .fence_token 盘丢也不会复活过期主(多数仍保单调 token);唯失去多数才 fail-safe 冻结。每个仲裁者各自持久化 token 到 <root>/.fence_token,其重启不清零。由此双写窗口被租约安全余量(WITNESS_LEASE_SLACK=500ms)界定——对端只能在我方租约到点后取 token,而我方提前该余量停止信任本地缓存租约(而非 peer-only 的不封顶)。由 test_ha.sh 段 9(过期 primary 重启被挡成 standby + token 持久化)、段 10(杀单 witness→自降级 & 拒绝盲升→恢复→恰好一主)、段 11(3 仲裁者宕 1 仍续租不冻、宕 2 破多数才 fail-safe)证明。
诚实标注:① 默认 async RPO ≈ 500ms,极端故障下最后 <500ms 的写可能丢失;加 --sync-repl 可把这批写的 RPO 降到 0。② fencing 需要第三仲裁者:严格两节点、不配 --witness 时无法防脑裂(CAP/共识硬边界,peer-only 双写窗口不封顶);配了 --witness 即 fail-safe——仲裁者多数派不可达时冻结写而非盲写/盲升;primary 持一份不重叠的有界租约(仲裁者拒发重叠租约,多数活租约即独占证明),写由本地租约校验放行、每续租一次对全列表 fan-out(摊薄到整窗),并对内容数据帧按 token 门控,把双写窗口收敛到租约安全余量内且保证收敛单主。多数派仲裁的可用性红利:--witness 取逗号分隔的 N 个独立仲裁者(推荐奇数),权威需多数派 N/2+1——宕掉少数仲裁者仍不冻结写(仅失去多数才停写),比单仲裁消除了 witness 这个单点可用性依赖(N=1 则退化为单仲裁旧行为)。代价:每续租一次向仲裁列表 fan-out。

Token 双面鉴权

中心 server 若裸监听 LAN,任何同网段主机都能按 key 读写对象/打开他人视图。加共享口令(同时覆盖数据面 OP_OPEN 与元数据面 M_OPEN):

内核自适应大块 IOmax_write/max_readahead 申请 4MiB，由 fuser 与内核按 FUSE_MAX_MAX_PAGES 各自截断：老内核（5.4）自动降到页上限，6.x+ 更大块=更少往返；PARALLEL_DIROPS、WRITEBACK_CACHE、MAX_PAGES 均能力协商。--stats 下会打印 grovefs negotiated caps: … 显示本机实际授予位。大块读写已贴近底层地板，实测 FUSE 每 op 仅加 ~50–70µs。
这些加速均为排障/调优观测，不构成吞吐或可扩展性声明（与论文边界一致）；上表数字是本机单进程 --stats 实测分布，存在 run-to-run 抖动但机制可归因。远程/PG 后端瓶颈是网络 RTT，须另用 bench_remote.sh 量测。

12.3 生成共享 token(强烈建议)

12.5 客户机:模板挂载单元(一个 view 一个实例)

mount 前台服务且内置 SIGTERM 处理:systemctl stop 会自动 fusermount -u 干净卸载,不留死挂载。

# /etc/systemd/system/grove-mount@.service —— %i = 视图名,挂载点 /mnt/%i
[Unit]
Description=GroveFS mount view %i
After=network-online.target
Wants=network-online.target
[Service]
EnvironmentFile=/etc/grovefs/grovefs.env
ExecStartPre=-/usr/bin/fusermount -u /mnt/%i   # 清掉上次异常退出的死挂载(- = 失败也继续)
ExecStart=/usr/local/bin/grove mount --view %i --data 10.0.0.5:50100 --meta 10.0.0.5:50110 --token ${GROVE_TOKEN} -m /mnt/%i
Restart=on-failure
RestartSec=2
[Install]
WantedBy=multi-user.target

# 拉起
sudo systemctl start grove-mount@alice          # 新 view 首挂即在中心按需建权威库,无需预先 init
findmnt -T /mnt/alice                           # 期望:grovefs:alice,FUSE
uid 两件事(见 §6.1):systemd 默认以 root 起挂载,上报 uid=0——开了 ACL 白名单就 acl allow --uid 0 或加 --as-uid N;要其他用户也能访问挂点,加 --o allow_other 并在 /etc/fuse.conf 打开 user_allow_other。

12.8 HA 主备拓扑部署

要点:两台 meta-server 用各自独立的 --db-path(快照复制,不是共享盘!blocks/ 才是共享的,客户机 --data 始终指向同一组 data-server):

# nodeA(10.0.0.5):primary;nodeB(10.0.0.6):standby —— 同样写成 systemd unit,只改 --db-path/--listen/--role/--peer
$Y meta-server --db-path /data/nodeA --listen 10.0.0.5:50110 --role primary --peer 10.0.0.6:50111 --token $TOK
$Y meta-server --db-path /data/nodeB --listen 10.0.0.6:50111 --role standby --peer 10.0.0.5:50110 --token $TOK
# 客户端故障转移列表;
$Y mount --view alice --meta 10.0.0.5:50110,10.0.0.6:50111 --data 10.0.0.5:50100 --token $TOK -m /mnt/alice
防双写需第三方仲裁:把 3 个(奇数)data-server 写进 --witness,且它们应与客户端实际写入的内容盘同节点部署(数据面门控只对列表内 data-server 生效,见 §9)。验收:ssh nodeA systemctl stop grove-meta-server → nodeB 日志出现 meta HA: promoted to primary at epoch N,客户机继续可写;旧主回来自动降级为 standby。

12.9 PostgreSQL 后端部署(只改 meta-server 一处)

# 1) 建库并给连接角色建 schema 的权限(view 首开时服务端幂等建表,无需预迁移)

13.3 恢复与节点修复三流程

  • 单机/本地模式:先 umount 停写(或停 meta-server),再 cp -a/rsync 整个 --home;恢复 = 拷回原位 → 重挂 → ls/cat 抽查。二进制不在备份范围——数据全在 --home。
  • SQLite + 自研 HA:备机坏了 → 修好后直接 systemctl start,它从主继续收 ~500ms 快照追平,无需手工灌数据;主机坏了 → 备自动提升,旧主修好 start 后见高 epoch 自动降级,配 --witness 时带旧快照重启也会被仲裁挡在 standby(test_ha.sh 段 9 证明)。两半全丢需重建:从归档快照恢复 <db-path>/meta/,且 epoch 重置的前提是所有 data-server 同时换新(否则残留 .fence_token 会挡住写——fail-safe 的正确行为,非损坏)。standby 的实时快照是复制体不是归档备份,仍建议定期对主/备任一侧做异地归档快照。
  • PostgreSQL 后端:视图树备份完全交给 PG 工具链(pg_dump/pg_basebackup + WAL 归档/PITR);GroveFS 侧只备 blocks/ + acl.db + env 文件。--store 模式下自研快照备份 API 有意返回错误(设计如此)。

13.4 升级与滚动变更

  • 客户端二进制(单台无中断):systemctl stop grove-mount@alice → 替换 /usr/local/bin/grove → start。直接 kill 不行——死挂载要 fusermount -u 手工清。
  • 中心 server(无 HA):替换二进制 → systemctl restart grove-data-server grove-meta-server,接受秒级 IO 暂停。客户机挂载进程不需要跟着重启——远程链路对 server 重启透明(resilience 套件:连接池整体丢弃后有限退避重连)。
  • HA 滚动升级:先升级并拉起 standby → stop primary(≤3s PROMOTE_TIMEOUT 内备提升,客户端自动切地址)→ 升级旧主并以 standby 拉起(自动降级回初始形态)。混版未经验证,同一次大版本升级请中心与客户机保持同版。

flock 看似被占住,持有者机器已整机崩溃等 ≤15s(LOCK_LEASE_SECS)lease 过期自动扫无 release 信号时 lease 是唯一兜底;正常进程崩溃是即时回收
data-server 重启后客户机 IO 卡一下又好了无需动作连接池整体丢弃后有限退避重连(resilience 证明)
allow_other 不生效/非 root 看不到挂点查 /etc/fuse.conf 的 user_allow_other;查 fusermount SUID 位FUSE 惯例限制,与 GroveFS 无关
--store postgres://… 加 --peer 启动即退去掉 HA 参数PG 与自研快照 HA 互斥是设计决定;高可用用 PG 流复制
大文件没看到条带分块确认文件 ≥16MiB 且 --data 给了逗号分隔多地址小文件自然只落 chunk0,是设计不是 bug
磁盘写满先扩 blocks/ 所在盘容量治理没有 magic:对象只增删不压缩,du -sh 监控

14.0 关于「数据库用 sqlite3」

不装任何东西:GroveFS 默认元数据引擎就是 SQLite,用 rusqlite bundled 把 SQLite 源码编译进了 grove 二进制——进程内引擎,不是需安装的数据库服务。不要给 meta-server 传 --store(传了才切 PG);权威树就是普通文件 /data/meta/share.db(+WAL 伴生文件)。有写活动时勿用 sqlite3 CLI 打开/裸拷该文件,备份流程见 §13.3。

14.2 存储机:目录 + token,并分发 env 到两台客户端

sudo mkdir -p /data          # 基目录;blocks/ 与 meta/ 都在服务首次启动时自动建

sudo bash -c 'umask 077; echo "GROVE_TOKEN=$(openssl rand -hex 16)" > /etc/grovefs/grovefs.env'

目录布局:/data/blocks/ 存文件真实字节(UUID 命名的扁平对象);/data/meta/share.db 存视图目录树;/data/meta/acl.db 只在用过 acl allow 后出现(§14.7)。视图与对象分离——目录项持 data_ref 指针关联两者。env 用 scp 分发到两台客户端的 /etc/grovefs/(chmod 600),三处 token 一一致。

14.3 存储机:手工起两个服务(先验后常驻)

# 窗口1 数据服务;TOK=$(grep -o '=.*' /etc/grovefs/grovefs.env | cut -d= -f2)
grove data-server --listen 0.0.0.0:50100 --root /data --token "$TOK"
# 窗口2 元数据服务(--db-path 指元数据根)
grove meta-server --db-path /data --listen 0.0.0.0:50110 --token "$TOK"
ss -lntp | grep -E '50100|50110'      # 两行都在即成功
参数取值意义
data-server --listen0.0.0.0:50100缺省 127.0.0.1:50052 只接本机,要接客户端必须显式 0.0.0.0;端口自定,客户端 --data 指对即可
data-server --root/data数据基目录:服务自动建其下 blocks/,字节以 UUID 平铺在 /data/blocks/;基目录指错 = 数据“找不回”
meta-server --db-path/data元数据根,视图库落 <db-path>/meta/;优先于全局 --home(后者仅兼容保留)
meta-server --listen0.0.0.0:50110同上(缺省 127.0.0.1:50053);元数据面单独占端口
两个 --tokenenv 那串分别把守 OP_OPEN/M_OPEN 两处握手;不带对 = 连接即 PermissionDenied,不重试
(不传 --store)—这就是“用 sqlite3”:embedded SQLite,一 view 一 .db
(不传 --role/--peer/--witness)—单权威节点;宕机 = 元数据面暂停(盘上数据不丢);要 HA 按 §12.8 扩

两个前台窗口应各打一行 banner——data-server listening on 0.0.0.0:50100、meta-server listening on 0.0.0.0:50110 (base /data, role Primary);完整终端效果见 §14.9 实录①。

14.5 客户端 A(192.168.1.11)读写挂载

sudo mkdir -p /mnt/da
TOK=$(grep -o '=.*' /etc/grovefs/grovefs.env | cut -d= -f2)
sudo grove mount --view share \
     --data 192.168.1.10:50100 --meta 192.168.1.10:50110 --token "$TOK" -m /mnt/da
参数取值意义
--home客户机不需传远程挂载不在本地落盘任何数据——权威库/白名单/字节全在服务端;此参数只属于本地模式(init/无 --meta 挂载);访问元数据根的命令(meta-server/acl)各自用 --db-path 命名,它仅作回退
--viewshare选树标签(与 Linux 用户名无关);A/B 同名才共享同一棵树;首挂时中心自动建库,无需预先 init

--meta192.168.1.10:50110目录树由中心 meta-server 提供——“多机共享一棵树”的根;同时订阅失效推送
--tokenenv 那串同时递给两处握手,不匹配 fail-fast
-m/--mountpoint/mnt/da是选项不是位置参数!裸写行尾路径实测报 unexpected argument;目录不存在自动创建

参数意义
--ro只读双保险:内核 MS_RDONLY + 文件系统侧守卫,所有写意图 op 一律 EROFS;其余参数与 A 完全同义

14.7 可选加固:服务端硬只读(视图白名单)

# 存储机：两个角色槽,只给 A 开写门
sudo grove acl --db-path /data allow --view share --uid 1001 --read --write
sudo grove acl --db-path /data allow --view share --uid 1002 --read
sudo grove acl --db-path /data list  --view share
# 两台客户端 ExecStart 换成下面两行全文后,各自 daemon-reload + restart
# A:/etc/systemd/system/grove-mount.service
ExecStart=/usr/local/bin/grove mount --view share --data 192.168.1.10:50100 --meta 192.168.1.10:50110 --token ${GROVE_TOKEN} --as-uid 1001 -m /mnt/da
# B:(--ro 保留,双保险)
ExecStart=/usr/local/bin/grove mount --view share --data 192.168.1.10:50100 --meta 192.168.1.10:50110 --token ${GROVE_TOKEN} --as-uid 1002 --ro -m /mnt/db
# 生效:
sudo systemctl daemon-reload && sudo systemctl restart grove-mount
参数意义
acl allow --view share --uid N --read [--write]往中心 acl.db 的 view_acl(view,uid,can_read,can_write) 写行;一旦有行,该 view 即白名单——没行的 uid 连挂载都被 E_AUTH 拒
--read(不带 --write)只读槽:读放行,每个写意图 op 服务端逐条动态重查回 EPERM——是鉴权拒绝不是故障;acl revoke 对存活挂载即时生效
--as-uid NM_OPEN 握手上报固定槽位代替真实 euid。systemd 默认 root 跑 = uid 0,白名单开了不给 0 授权则拒挂——两台都必须显式声明。advisory:防误操作不防伪造,真准入靠 token

14.8 案例验收清单 + 回退

  • ① 存储机两服务 is-enabled/is-active 双绿(开机自起 OK)。
  • ② A 写 → B 秒读;B 写 → EROFS(配了 ACL 后即使去掉 --ro 重挂也 EPERM)。
  • ③ 字节在中心:ls /data/blocks | head 见 UUID 对象随写入增长;share.db 存在且变大(勿直接打开它)。
  • ④ 中心 systemctl restart grove-data-server 后客户端 IO 自动重连(resilience)。
  • ⑤ systemctl stop grove-mount 后 findmnt 无残留;回退 = 客户端 stop → 存储机 disable --now,/data 不删即完整备份(§13.2/13.3)。

15.2 存量大量数据进来:两条正路,首选零拷贝 grove import

首选——原地登记不搬家(同文件系统,§15.7):字节零复制、秒级完成、时间戳/权限保真。需要重组数据、PG 后端、或想让大文件享受条带时,走备选——经 FUSE 写路径灌入:

# 首选：在存储机一条命令登记整棵已存在的目录树（不读内容、不占额外盘）
grove import --db-path /data/cluster --view legacy --source /data/legacy --prefix /legacy
# 备选：在任一台已挂载客户端分批灌入（层级随写自动成型）
rsync -a /srv/legacy/ /mnt/da/imported/
# ≥4MiB 写自动分片并发；多地址且 ≥16MiB 自动条带——导入无需特殊调优
ls /data/blocks | head && find /mnt/da/imported -maxdepth 2 | head   # 抽验

取舍：import 零拷贝但导入对象是单文件（不走条带）、向在线挂载靠 TTL 收敛；rsync 灌入多一份字节但可条带、即时推送。经 FUSE 写入的吞吐上限在帧链路与中心盘，TB 级存量低峰分批；百万级文件会让 view.db 相应增长，属正常。

15.3 客户端“显示方式”的五个机制

机制效果适用
不同 --view = 不同树完全独立层级，互不可见A/B 看根本不同的东西
同 --view = 同一棵树字节一份，所有挂载点同一棵权威树(实时同步)；B 只读用 --ro/ACLA/B 共享同一批数据
mount --layout 显示透镜(§15.5)同一棵树，每个挂载点自行 hide/only/map/link：部分显示、重组路径，字节不动定制显示形状，不需两份数据
服务端派生视图(§15.6)同一套透镜规则命名后集中存在服务端(meta/views/)，客户端只 mount --view <派生名>：同名跨机同形、可按名配 ACL；派生(虚拟)视图挂载一律只读(写走基名)团队共享显示契约、免分发规则文件；只读分发形状

树内多入口：硬链+软链同一份字节摆出多种组织(按年/按类/快捷入口)同 view 内多视图目录
cd /mnt/da

rm imported/report.pdf                             # 安全：硬链接还在，对象不会被删

GC 语义(源码保证)：对象只在最后一个引用它的目录项消失时才删；refcount 读写同一事务，并发硬链不误删不泄漏。软链接不占引用，真删目标后悬空；不要拿软链接指另一个 view 的路径(另一棵树在该挂载点根本不可见)。

15.4 “B 只想看到一部分”：现有三条路 + 未实现清单

  1. mount --layout 显示透镜(§15.5)，或其服务端集中定义版——派生视图(§15.6)：B 的挂载加 only /by_public 或 hide /photos/private(本地规则)，或由管理员 grove view define 后 B 直接 mount --view <派生名>(免分发规则文件、可按名配 ACL)——字节零复制、其它挂载无感；但两者都是显示定制不是硬安全边界(B 不带透镜/直挂基名仍见全树，拦住他的是 ACL/token)。区别在写权限：派生(虚拟)视图挂载一律只读(形状由服务端治理，写只能走基名)，而客户端自备的 --layout 透镜仍可写(直写真实条目)——B 需要可写形状就用 --layout，只要只读分发形状就用派生视图。
  2. 同 view + 目录约定：B 只进 by_public/ 这类发布目录——简单，但约定不是强制(B 能 cd 到任何地方)。
  3. 拆两个 view + 灌两遍：share_pub 只放可公开内容(rsync --include/--exclude 筛)，B 挂它配 ACL——硬隔离真只读，代价是公开部分字节多一份。要真安全隔离选这条。

未实现(诚实标注)：子树挂载 --subpath/--prefix(--layout only/hide 是显示裁剪，不是路径 chroot)；跨 view 硬链接/共享对象(link 只在树内，分视图即两份字节)；导入后源目录的持续自动同步(watcher/定时重扫)——grove import 是手动幂等增量命令；per-directory ACL(粒度是 view × uid；--layout 可做目录级显示裁剪但不构成强制隔离)。

15.6 服务端派生视图：grove view define + mount --view <派生名>

§15.5 的透镜规则由各客户端自备；想把形状集中管理在服务端（团队共享一个显示契约、按名授权），用派生视图：grove view define 把规则写进 meta 根的 <db-path>/meta/views/<name>.layout（首行 base <物理视图>，余行即 §15.5 四动词），客户端只 mount --view <派生名>，不需本地规则文件。派生（虚拟）视图一律只读挂载——形状集中治理、只分发不修改，写入只属于原（基名）视图；要可写的自定义形状用 §15.5 客户端自备的 --layout 透镜：

命令参数释义效果

grove view --db-path D list—列出全部派生视图及其 base/规则计数

15.8 纯别名：名字治理：grove view alias

§15.6 的派生视图治理“长什么样”；纯别名治理“叫什么”：名字就是别名，映射值才是真实名。定义同放 <db-path>/meta/views/<name>.layout，首行 alias <真实视图>、不带任何规则行。与派生视图恰成正反两面：别名挂载全树可写(它就是真实视图的原形)，而真实名从此不是挂载入口——本地(--home)与 meta-server 都拒挂被治理的真实名：公开名与存储身份解耦，对外名字可自由轮换，猜出真实名也挂不进来：

命令参数释义效果
grove view --db-path D alias --name A --real RA=公开名，R=物理视图名写入/替换 D/meta/views/A.layout(内容仅 alias R)；挂 A=全树可写；R 从此不可直挂(本地与服务端均拒)
挂载无任何额外参数mount --view A 即得真实视图全树；远程在 M_OPEN 服务端解析，ACL 按真实名判定(解析在读门之前)，acl allow --view R 一条授权对别名与基名同时生效
grove view --db-path D rm --name A—删别名，真实名对新挂载恢复可挂(已建立连接不受影响)
grove view --db-path D alias --name A2 --real R --retire AA2=新公开名，A=被泄露的旧别名原子轮换：先写 A2 再删 A，真实名 R 全程被治理、无裸露窗口；旧名 A 立即失效(挂它只落到一个按需新建的空视图，触不到真实树)；ACL 记在 R 上故授权不动，合法用户改用 A2 重挂即可

$ echo hello > /mnt/work/docs/2026/new.md   # 别名写入即真实树，经派生名挂载穿透可见
$ grove mount --view team -m /mnt/t --meta 10.0.0.5:50241 --data 10.0.0.5:50240   # 直挂被治理的真实名：服务端拒挂

守卫(alias 命令处 fail-fast，layout 套件第 10/11 节 26 条断言)：拒 name == real、拒遮蔽物理 <name>.db、拒目标是派生视图(别名只映射物理视图)、拒别名链(--real 指向另一个别名)、一个真实视图同时只允许一个对外名(--retire 在同一条命令内先写后删、不受此约束卡住，且拒指向派生视图或不存在的别名，不会误删形状定义)；define 也拒遮蔽已有别名名。本地(--home)同契约：挂载先解析 views/<name>.layout，别名换名后照常挂载并打印 alias view 'A' resolves to real view 'R' (full tree, writable)；直挂被治理真实名回 "view 'R' is governed by an alias"；grove import 拒别名目标(别名不是存储身份，写出无人可读的影子 db)。实现事实：别名解析单跳、每 M_OPEN 重扫 views/ 目录(挂载罕见事件，小目录全读比维护失效协议便宜)，已建立连接不受定义增删/轮换影响(同读门语义，轮换/rm 只作用于新挂载)；被轮换掉的旧名落到按需新建的空命名空间、触不到真实树，故泄露无害；meta/views/ 是普通文件，HA 备机随 acl.db 手工同步。如实标注：远端拒挂真实名时客户端回显复用 "meta-server rejected the access token" 文案(E_AUTH 共用码，拒因字节未入协议，行为正确、提示不精确)，本地拒挂文案精确；轮换是名字治理(泄露止损)而非安全边界——公开名终究要分发，且轮换不能撤销一个已持有 token 者的既有访问，硬边界仍是 token+ACL。

15.9 智能体定制数据列表：MCP 接口：grove mcp

§15.6/§15.8 的视图治理同时是一套 MCP(Model Context Protocol)工具：grove mcp 在 stdio 上说换行分隔的 JSON-RPC 2.0(实现 2025-06-18 协议的常用方法面：生命周期 initialize/ping、工具 tools/list/tools/call、资源 resources/list/resources/templates/list/resources/read、提示 prompts/list/prompts/get、补全 completion/complete、日志 logging/setLevel 与服务端 notifications/message；客户端通知一律静默不作答)，任何 MCP 客户端(Claude Desktop、IDE 智能体等)把它当子进程拉起，智能体即可通过接口自动定制数据列表的形状——查视图、探查某视图真实呈现的目录清单并按绝对显示路径写规则(list_view_tree 经已发布透镜渲染、还能不落盘预览一副待发布规则的形状，get_view 读回单个定义原文)、用内联规则文本发布只读派生透镜、轮换公开名、删定义、发布前把整副定义走完全部治理守卫做干跑校验(validate_definition，不写盘)；规则以文本随行(hide/only/map/link，同 --layout 四动词)，智能体不需要碰任何文件。八个工具与 grove view 子命令共用同一套库函数(grovefs::mcp)：一个契约、两个入口，校验/拒绝文案/落盘动作逐字节相同，智能体做不出 CLI 做不出的事，也绕不过任何守卫。

17诚实标注的边界

以下为本项目遵循"工程诚信"原则明确标注的限制,而非隐藏假设:

  • 传输协议:当前为自定义 TCP 帧,非 gRPC。gRPC(tonic/prost)已做 go/no-go 闸门评估,结论 GO(tonic 0.14 免 protoc),但完整集成有意延后——独立可弃的末位项,现协议已正确且被测。
  • HA:RPO ≈ 500ms(async;--sync-repl 可降到 0)。真 fencing 依赖仲裁者:--witness(逗号分隔的 N 个共享 data-server 作 prev-回传 epoch CAS 多数派仲裁,需 N/2+1 授予)已落地并 fail-safe——仲裁者多数派不可达时冻结写而非盲升;primary 持不重叠的有界租约(仲裁者拒发重叠租约,多数活租约即独占证明),写由本地租约校验放行、每续租一次向全列表 fan-out,并对内容数据帧按 token 门控,把双写窗口收敛到租约安全余量内(保证收敛单主),各仲裁者独立持久化 token 防重启复活;宕少数仲裁者仍不冻结写、少数盘丢不复活过期主(N=1 退化为单仲裁旧行为)。仅严格两节点不配 witness 时仍无法防脑裂、窗口不封顶(CAP 硬边界,须部署第三方仲裁)。
  • 条带:单条饱和链路无吞吐增益,价值在多节点聚合容量;真实多机链路须重测后才可声称收益。
  • 验证环境:全部在 127.0.0.1 回环(模拟 LAN)验证,尚未做真实多机与 fio 级基准。
  • 视图白名单 uid:客户端上报 uid 属 advisory(TCP 客户端可伪造或 --as-uid 覆盖),真正的集群准入仍由 --token 把关;白名单适合已通过 token 的集群内部分工,不适合防内鬼或多租户外部隔离。只读授权连 flock/共享锁也会被拒(锁 op 归写意图);读门仅挂载时校验,撤读对已建立连接到重挂才生效(写门才是逐 op 即时)。
  • 显示透镜 --layout:是显示层定制而非安全边界——绕过透镜直接挂同一 view 仍见全树,硬隔离用独立 view + ACL/token;向纯合成目录创建/重命名进入返回 EPERM、撞透镜已显示名返回 EEXIST、only 模式白名单外不可写;symlink 目标文本不改写;共享 meta-server 下合成目录条目失效推送可能不命中透镜坐标(建议 --strict);规则限同一 view 内部重排,不支持跨 view 引用。
  • 服务端派生视图 grove view：一律只读挂载(硬契约)——形状集中治理、只分发不修改，写只属于基名视图；三层强制(M_OPEN 协商内核 RO→客户端 EROFS；服务端派生名逐 op 权威门禁回 E_NOTPERM；本地 --home 挂载时同判)。若需可写的自定义形状，用客户端自备的 mount --layout 透镜(§15.5，直写真实条目)。其余：同样不是安全边界——直挂基名仍见全树(拦住他的是 ACL/token,不是形状);define 替换热生效(服务端逐 op 检查定义 mtime,已挂载连接 ≤2s TTL 内自动换形、免重挂,换形后只读契约不变),view rm 不热作用(已挂载者保持旧形状到重挂);换形时旧虚拟 ino 上的合成路径/fd 可能落回 ENOENT,真实条目 inode 稳定不受影响;不嵌套(base 须是物理视图)、不得与基同名、不得遮蔽物理 db;meta/views/ 是控制面配置,HA 备机需手工同步(同 acl.db);热重载仅限 meta-server,本地(--home)挂载仍在挂载时解析一次。
  • 服务端纯别名 grove view alias：与派生视图的正反面——别名挂载全树可写、真实名被治理后不可直挂(本地与服务端均拒)；单跳解析、每 M_OPEN 重扫 views/(挂载是罕见事件)；拒别名链/派生目标/一真实名多别名；import 拒别名目标；删别名仅影响新挂载(已建立连接不受影响，同 view rm 语义)；远端拒挂真实名时客户端回显复用 token 拒因文案(E_AUTH 共用码，行为正确、提示不精确)，本地拒挂文案精确；改名不是安全机制(公开名终究要分发)，真实名隐藏属名字治理，硬边界仍是 token+ACL。
  • 智能体接口 grove mcp：把视图治理以 MCP 工具暴露给智能体，与 grove view 共用同一套库函数(一个契约、两个入口，校验/拒绝文案/落盘动作逐字节相同)，智能体做不出 CLI 做不出的事、也绕不过任何守卫。控制面 only：不挂载、不读不写数据；默认信任能启动此进程的调用方(跨网准入仍由服务端 token/ACL 负责)，但 --require-api-key 可选地为接口上 API key 门(grove apikey 铸造/列表/撤销、只存 SHA-256、调用日志归属，见 §15.9.1)。热生效仅限 meta-server 入口(本地 --home 挂载解析一次)。已覆盖 2025-06-18 协议的常用方法面(手写 JSON-RPC，未引框架 crate)：生命周期 initialize/ping、工具 tools/list/tools/call、资源 resources/list/resources/templates/list/resources/read、提示 prompts/list/prompts/get、补全 completion/complete、日志 logging/setLevel 与服务端 notifications/message；客户端通知一律静默不作答。这些读面均复用与工具同一套治理渲染器(grovefs::mcp)，故资源/提示/补全结果与工具结果逐字节一致，不引入独立逻辑；尚未做的是资源订阅(subscribe)与各面的 listChanged 推送(当前均声明为 false)。
  • 零拷贝导入 grove import:硬链接要求源与 blocks/ 同文件系统(跨盘自动退化为独立拷贝并如实计数);外部工具以 rename/替换写更新源文件(vim 默认行为)时,视图侧保持旧 inode 的最后内容,需对新内容重跑 import(已有名字跳过,可换 --prefix 强制重登记);symlink/特殊文件有意跳过;导入对象为单文件,不走 ≥16MiB 跨 server 条带;meta-server 部署下 import 直写权威 db 文件,需在存储机执行、已挂载靠 TTL(≤2s)收敛而非即时推送;PG 后端不支持(权威树在 Postgres,走挂载点 rsync 灌入);--source 建议与存储根同盘并保留——删源仅失去「源路径」别名(数据在 blocks/ 链接里不丢),但外部改名/迁移后视图与字节实体的关联只剩 blocks/ 一条路径。
  • PostgreSQL 后端与 HA 互斥:--store postgres://… 下自研 HA(--role standby / --peer / --witness)在启动时 fail-fast;backup_to_bytes 返回错误——高可用请交给 PG 自带的流复制 / logical replication / PITR,不在 GroveFS 里重一个共识。ACL 白名单在 PG 模式下随元数据面迁入同一实例的共享表 grovefs_acl.view_acl（grove acl 须带同款 --store URI）。
  • 元数据读并行 / 目录分页的作用范围:只读连接池与 LIMIT/OFFSET 分页现在长在两个存储引擎(SQLite MetaEngine 与 PG PgEngine)里,各自 4 连接只读池。本地 --home(SQLite 或 PG)吃满分页与 PLUS;meta-server 的并发处理器吃各自后端的池,且新增的 M_READDIRP 帧带 offset/limit 把分页下推到服务端,远端客户端每缓冲只取一页并协商 FUSE_READDIRPLUS(同一 5001 条目录远端实测由改造前 ~54s → 2.29s,只关 PLUS 保留分页 4.22s)。仍走 trait 默认实现(每缓冲一次全量列表、不协商 PLUS)的只有 LayoutMeta 派生/透镜(隐藏/映射形状无法表示为单条 SQL 页)与对接不含该能力位的老 meta-server 的挂载(M_OPEN ack 无第二字节则回退)。元数据写并行已覆盖 PG 后端(单集群内 SERIALIZABLE 写池,见 §6.2);跨节点多权威/分片的写扩展仍未做。判据 MetaProvider::supports_paged_readdir() 由单测 store_level_paging_is_advertised_only_by_providers_that_page_in_sql 钉住。
