1是什么 / 核心概念

一句话：把「谁能看到什么（视图）」和「字节实际存在哪（对象）」拆开。每个用户一棵独立目录树，互不可见；字节统一落在物理块目录里，只存一份。

视图 view

每个用户一棵独立目录树（层级自定义，互不可见）。SQLite 部署是 <db-path>/meta/<view>.db；PG 部署是一个 grovefs_v_<hex> schema。

数据对象 object

文件的真实字节：blocks/ 下一个 UUID 命名的对象（大文件可条带成多块）。目录项只存对象 key，不存字节。

基目录 --home

仅单机模式需要：blocks/ + meta/ 的本地根。服务/客户端模式不用它——远程挂载本地零落盘，存储机各命令用自己的 --db-path / --root。

三句话记住：
  • 视图 = 目录树 + 指针，字节永远在 blocks/；删名字不等于删字节（最后一个引用才回收）。
  • --view 是任意标签，不是 Linux 用户；两台机器挂同一个 --view alice = 看到同一棵树。
  • 权限看 token / API key，不看系统 uid；隔离粒度是整棵视图树，不是单个路径。
--view 到底是什么？（跟 Linux 用户名没关系）

它不调 getpwnam、不校验 uid、不要求 useradd。alice、team-a、u42、研究组 都可以，只用作两处：① 库名/schema；② 挂载点上显示的 grovefs:<view> 标签。

树内可以 mkdir/touch 任意多个文件与目录、任意深度，与自家 home 无差异；--manifest 只是预建骨架的入口，不是路径数量上限。

鉴权不来自 Linux 身份，而来自能访问存储根 + 服务端准入（可选 --token，或可撤销的 --require-api-key + mount --api-key）。

2架构与原理

三层解耦,全走 trait 抽象:

┌─ FUSE 挂载进程  fs_impl.rs:GroveFS(&self, 多线程安全)
│    ├── MetaProvider trait  视图树访问(12 方法)
│    │     ├── 本地:  MetaEngine  → <home>/meta/<view>.db
│    │     └── 远程:  RemoteMeta  → meta-server(中心权威)
│    └── StorageBackend trait 数据对象 IO
│          ├── 本地:  LocalBackend → <home>/blocks/<key>
│          ├── 远程:  RemoteBackend → data-server
│          └── 条带:  ShardedBackend → 多 data-server
└─ 传输:自定义二进制帧 over TCP(定长头+变长体),连接池并发

为什么这样设计

  • trait 接缝可插拔:本地/远程/条带对上层透明,切换只是换个实现。
  • 中心 MetaServer:同一用户在多客户机共享一份权威视图,不再各存各的副本导致分叉。
  • 事件总线 + Notifier:写成功后向订阅者推送失效,解决"默认缓存下内容新鲜度"。
  • fuser 0.18 多线程:每线程独立 /dev/fuse fd(clone_fd),请求并发派发不串行。
  • 元数据读并行 + 目录分页 + READDIRPLUS:每个视图引擎除单条写连接外再开 4 条只读连接(SQLite READ_POOL_SIZE / PG PG_READ_POOL_SIZE)服务 lookup/getattr/readdir,读不再排在写锁后面;目录列举按 readdir_page 下推成 SQL LIMIT/OFFSET,回复缓冲按 32→1024 几何块填充,一次内核请求付 O(缓冲) 而非 O(整棵目录);默认协商 FUSE_DO_READDIRPLUS(内核 ≥4.6)让属性随目录项一次带回。写侧:SQLite 仍串行在同一权威连接,PG 走 SERIALIZABLE 写池并行(见 §6.2)。
实测：5001 条目录的 ls -l 从 55s 降到 2.5s（怎么量的、谁吃不到）
  • 本地：同一份 5001 条目录、同一挂载点、每趟新挂载实测 ls -l 2.56s（只留分页 5.22s；改造前基线 55.34s，三份输出排序后逐字节相同）。
  • 远端：新 M_READDIRP 帧把 offset/limit 下推到服务端，同一目录经 meta-server+data-server 由 ~54s → 2.29s（只关 PLUS 保留分页 4.22s，两份输出逐字节相同）。
  • 覆盖范围：本地 SQLite/PG 与对接 SQLite/PG meta-server 的远端挂载都启用；仅派生/透镜视图与不含该能力位的老服务端仍走每缓冲一次全量列表、不协商 PLUS。

一次写请求的完整路径（数据面 / 元数据面各走一半）

app write()/close()
   ├─ 数据面   → RemoteBackend ─TCP帧→ data-server → blocks/<2hex>/<key>（UUID、256 桶自动扇出）
   │                                    ≥4MiB 分片并发；大文件跨多 data-server 条带
   └─ 元数据面 → RemoteMeta   ─TCP帧→ meta-server → 权威视图树（默认 SQLite，或 PostgreSQL）
          create / rename / setattr / touch_mtime …
          └─ 写成功 → 事件总线推 inval_entry+inval_inode → 对端下次访问即时可见
  • 谁持有权威：meta-server 是单一权威串行点——同一 view 的一棵树只由这一个进程落到存储引擎（SQLite 一 view 一 .db，PG 一 view 一 schema），所有客户端经 TCP 帧汇聚到它。有意为之（杜绝各存副本导致的视图分叉），不是疏漏。
  • 客户端从不直接碰存储：既不开 .db 文件、也不持 PG 连接串，只说 GroveFS 线协议；后端是 SQLite 还是 PG 对客户端完全透明、命令一字不变。

3快速上手(单机本地模式)

数据和视图都在本机同一个 --home,无需任何 server,先体验功能最快。

Y=./target/release/grovefs
BASE=/data/myfs                       # 物理基目录

# 1) 初始化两个用户的视图
$Y --home $BASE init --view alice
$Y --home $BASE init --view bob

# 2) 挂载(默认转后台:挂载点就绪即返回,只打一行摘要;前台附着用 --foreground)
$Y --home $BASE mount --view alice --mountpoint /mnt/alice
$Y --home $BASE mount --view bob   --mountpoint /mnt/bob

# 3) 像普通目录一样读写、建自定义层级
mkdir -p /mnt/alice/projects/2026
echo "年度报告" > /mnt/alice/projects/2026/报告.txt
ls /mnt/bob                                      # bob 看不到 alice 的文件

# 4) 卸载
$Y umount --mountpoint /mnt/alice
视图隔离:/mnt/alice 与 /mnt/bob 是两棵独立的树,互不可见;层级(mkdir 嵌套目录)完全自定义。
命令瘦身:重复敲的长参数可以整体瘦身——每个旋钮取值优先级恒为命令行参数 > 当前环境变量 > 配置文件 > 内置默认值。启动时自动加载一个 KEY=VALUE 文件(查找顺序:$GROVEFS_CONFIG > ~/.grovefs/grovefs.conf > ~/.config/grovefs/grovefs.conf,首个存在的生效)填入尚未设置的 GROVEFS_* 环境变量:GROVEFS_HOME(--home)、GROVEFS_META/GROVEFS_DATA/GROVEFS_TOKEN(mount 与两个服务端的对应参数)、GROVEFS_DB_PATH(meta-server --db-path)、GROVEFS_API_KEY/GROVEFS_MCP_API_KEY/GROVEFS_STATS。语法支持 # 注释、export 前缀、引号值;非 GROVEFS_* 键与坏行带文件名:行号警告后忽略。文件里有口令就 chmod 600(与 env 里放口令同一契约);--view/-m 刻意不收录(每次挂载都不同)。典型效果:grovefs mount --view alice -m /mnt/alice 即可,中心地址与 token 全进文件。回归:config 套件 28 断言(见 §11)。

4用 manifest 预建自定义层级

init --manifest 在建视图时一次性铺好目录骨架。每行仅两种指令:mkdir <path> 或 touch <path>,行首 # 为注释。

# seed.txt
mkdir projects
mkdir projects/2026
touch projects/2026/README.txt
$Y --home $BASE init --view alice --manifest ./seed.txt
# 输出:applied seed manifest ./seed.txt

挂载后即见预建层级;重复 mkdir/touch 幂等,不报错。

5生产拓扑:中心存储 + 多客户机 LAN 挂载

真实场景:数据放中心集群,多台客户机经 LAN 挂载,同一用户跨机器看到同一份权威视图。拆成两个服务:

# ===== 中心节点 =====
$Y data-server --listen 0.0.0.0:50100 --root /data/cluster
$Y meta-server --db-path /data/cluster --listen 0.0.0.0:50110

# ===== 每台客户机(远程挂载不需要 --home,本地什么都不落) =====
$Y mount --view alice \
     --data 10.0.0.5:50100 --meta 10.0.0.5:50110 -m /mnt/alice
选项作用
--data host:port文件 IO 走网络到 data-server,不碰客户机本地盘(非 NFS)。
--meta host:port视图由中心 meta-server 提供 → 多客户机挂同一用户 = 共享同一棵权威树。
--data a,b,c逗号分隔多地址 → 启用跨 server 确定性条带(见 §8.2)。
--meta 主,备故障转移列表,主挂自动切备(见 §9)。

客户机本地不留视图副本、也不落盘：给了 --data/--meta 的远程挂载不需要 --home（传了也不写任何东西）——字节直连 data-server，视图树直连 meta-server，访问控制全部在服务端。

视图名不存在时的两种模式：默认懒创建——第一次 M_OPEN 就建出 meta/<view>.db（PG 后端为 grovefs_v_<hex> 空 schema），客户端挂载成功但看到空目录，所以拼错名字不会报错。给 meta-server 加 --strict-view 则相反：名字必须已经有树或治理定义（派生/别名/fork 都算），否则握手直接拒绝，而且服务端什么都不写；拒绝原因带可读文本（客户端打印出来，不再只是 Input/output error，服务端日志同一句），开了 --require-api-key 时还进 apikey calls 审计。严格模式下建新视图要先建后挂：SQLite 用 init --view / view import；PG 没有离线 init，先不严格挂一次建出 schema 或从 dump 恢复。细节与实测输出见 USAGE §4。

6共享视图与权限模型

GroveFS 的权限栈只有两层——令牌 = 集群准入，view 名 = 树选择。--view 字符串本身不是身份：任何 uid 只要挂同一个 --meta <addr> + --view alice 都会落到 alice 的同一棵权威树上，看到彼此写入。这是有意的，也让“多人共享一个视图”开箱即用。

一图看懂：客户端(viewer) → 门控 → view → 存储

隔离单位是 view 名，不是客户端——N 个客户端 ↔ M 个 view（多对多），
隔离单位是 api key 的视图绑定 (--view) / 只读 (--ro)(<db-path>/meta/api_keys.db；PG 后端为 grovefs_control.api_keys) 决定「哪个调用方能开哪棵 view、读写还是只读」（铸造见 §10/§15.9.1）

客户端 A · uid=1000   mount --view alice ─┐
客户端 B · uid=2000   mount --view alice ─┤ 同一个 --view → 落进同一棵树；一个客户端也可
客户端 C · uid=1000   mount --view bob    ─┘ 同时挂多个 view（多对多）
        │
        ▼  TCP 帧 M_OPEN(view, token, uid, api_key)   客户端从不开 db 文件 / 不持 PG 连接串
┌─ meta-server（单一权威写者）—— 按序过门，再路由
│   ① token 校验   不匹配 → E_AUTH（集群准入，唯一确定性门；uid 自报属 advisory）
│   ② api-key 门 服务端 --require-api-key 时：scope 非 mount/any、缺失/无效/已撤销 → E_AUTH（带拒因原文）；key 若 --view 绑定，开其它视图同样握手即拒
│                  活连接每秒复证一次（有流量才查），撤销即断开该挂载并使其自卸载
│   ③ ro 写门 key 若 --ro：每个写意图 op 直接 E_NOTPERM（data 面内容写 EROFS），M_OPEN 回包告知只读挂载
│   ④ view 名 → 引擎缓存  首次 M_OPEN 懒开，之后同 view 命中同一实例
└──┬──────────────────────────────────────────
   ▼ view=alice                        ▼ view=bob
  alice 权威树（A、B 共享，写串行化）    bob 权威树（仅 C，与 alice 互不可见）
   ├── SQLite（默认）： 一 view = 一个独立 db 文件  <db-path>/meta/alice.db · bob.db
   └── PostgreSQL（--store）：一 view = 一个独立 schema grovefs_v_616c696365 · grovefs_v_626f62

结论：数据库里独立存储的单位是「视图」而非「每个客户端」；alice 的树不管被几台机器挂都只有这一份。
数据面与视图树解耦：文件字节走 data-server → 存进其 --root 下的 blocks/<key>，树里只存 data_ref 引用。
多机 LAN 共享一棵树需要 PG 吗？——不需要。共享能力来自「同一个 meta-server + 同一个 --view」，与底层是 SQLite 还是 PG 无关。默认 embedded SQLite（零外部依赖）就支撑多客户端挂载、写串行化、实时失效推送，已由 metasrv/freshness/locks 套件在纯 SQLite 上证明。PG 只在服务端：--store 是 meta-server 独有的选项，客户端没有、也不感知。
那什么时候该换 PG？（两者二选一，不是叠加）
  • 替代关系：同一棵权威树只落在其中一种后端上。用 SQLite 就不需要装 PG；换 PG 后视图树不再落 .db 文件，控制面（视图定义 / 密钥 / 审计）也一并进 PG 的 grovefs_control schema，本地不留任何控制面文件。
  • PG 的增量价值：把持久化 / HA / 备份 / PITR 交给成熟数据库，外加元数据写并行。
  • 写并行（PG 独有，opt-in）：SQLite 后端对同一 view 是单写者（一条权威连接 + 互斥锁，写串行）；换 --store postgres://… 后写路径放宽为至多 8 连接的 SERIALIZABLE 写池（HopsFS 路线，事务基座交给 PostgreSQL 自带 SSI），不相交行上的并发写真正并行提交、冲突侧透明重试（详见 §6.2）。

6.1 多人共享同一 view（逐调用方差异化权限 = 视图绑定 / 只读 key）

多台机器、不同 OS 用户，都 mount --view alice --meta … --data …，就落进同一棵树：元数据经 meta-server 集中（一棵 SQLite/PG 树，串行化写）、内容经 data-server 集中（一份 blocks/）；ls 或 cat 立刻跨端可见，实时失效推送保证收敛。

若需在同一棵共享树里区分职责（只读审阅者，或限制某调用方只能碰某棵视图），给每个角色铸一把视图绑定 / 只读 API key——在中心元数据根上铸造（--db-path 与 meta-server 同名同目录）：

# rw 协作者：只能开 alice、可读写
$Y apikey --db-path /data/cluster create --label coworker --for mount --view alice
# 只读订阅者：只能开 alice、且写一律被服务端拒
$Y apikey --db-path /data/cluster create --label reader   --for mount --view alice --ro
$Y apikey --db-path /data/cluster list                                          # 查看 view / rw 列
$Y apikey --db-path /data/cluster revoke --id <ID>                              # 撤销（支持唯一前缀）

两个维度：绑哪棵树 / 能不能写

  • 视图绑定 --view V：key 只能开 V，开别的视图在 M_OPEN 处即 E_AUTH 拒（携拒因原文）；省略 --view 则是可开任意视图的系统级 key。
  • 只读 --ro：每个写意图 op 在服务端逐 op 动态重查、回 E_NOTPERM（客户端 FUSE 侧落 EPERM，data 面内容写 EROFS，区别于 HA 备机的 E_ROFS 故障转移信号）；读照常放行，M_OPEN 回包并提示客户端只读挂载。

凭据存在哪、怎么收回

  • 存放：SQLite 部署是控制面库 <db-path>/meta/api_keys.db（表 api_keys(id, label, secret_hash, scope, view, ro, revoked_at)）；PG 部署是 grovefs_control.api_keys，无本地文件（控制面随元数据后端走，见 §6.2）。key 明文仅在 create 时打印一次，库里只存 SHA-256。
  • 撤销：revoke 只把行标记为 revoked（历史调用保留归属）；服务端每秒在有流量的连接上复证一次，被封挂载打印服务端拒因后干净自卸载（不留 Transport endpoint is not connected），其他 key 的挂载不受影响。
  • uid 只用作归属：客户端上报 uid 默认 geteuid()、可 mount --as-uid N 覆盖，只记进锁仲裁与审计，从不作为访问控制门。

两个必须知道的行为边界

  • 加锁类 op 归写意图：flock/F_SETLK（含锁续约）要写中心 locks 表，只读 key 对它们一律 E_NOTPERM→EPERM；只读角色若需共享锁做读协调，得改用一把读写 key。
  • 撤销是 op 驱动：封停边界是「撤销后的首个服务端往返」——完全由内核缓存回答的读不需往返、不会被打断（下一次往返即封）。
诚实边界：TCP 客户端自报 uid 属 advisory（客户端可伪造），真正的集群准入由 --token / --require-api-key 把关，「谁能碰哪棵树、读写还是只读」由 key 的 --view/--ro 绑定在服务端硬强制。由 mountkey 套件 64 条断言证明（视图绑定 key 跨视图拒挂与审计归属 / 只读 key 服务端强制写拒）。

6.2 元数据后端可切换：SQLite ↔ PostgreSQL

仅指 meta-server 的权威存储；客户端看到的线协议不变。默认 embedded SQLite（一 view 一 <home>/meta/<view>.db），也可以整体换为 PostgreSQL：

  • 二选一，不共存不叠加：给了 --store postgres://… 后视图树只进 PG schema，不再创建或打开任何视图 .db；db-path 里留下的 .db 只是换库前的旧副本，服务端不再读写它。
  • 控制面跟随后端：视图定义 / 密钥 / 审计全进共享 schema grovefs_control（view_defs / api_keys / mcp_calls），grovefs view / apikey / mcp / data-server 加 --store（或 env GROVEFS_STORE）接同一 URI，本地不落任何控制面文件。
# 默认（SQLite）
$Y meta-server --db-path /data/cluster --listen 0.0.0.0:50110

# PostgreSQL：一 view 一个 schema grovefs_v_<hex(view)>，事务化 rename/unlink/lock
$Y meta-server --db-path /data/cluster --listen 0.0.0.0:50110 \\
     --store postgres://user:pw@10.0.0.9:5432/grovefs

# 客户端命令完全一致（仍 --meta host:port --view alice）
$Y mount --view alice \\
     --data 10.0.0.5:50100 --meta 10.0.0.5:50110 -m /mnt/alice
  • 中途换库是单向搬移：用 view export/import（目前只面向本地 SQLite 树）或 pg_dump 搬一次，不支持双写；换库步骤见 §14.9。
  • PG 模式与自研 HA 互斥：--store postgres://… + 任一 --role standby / --peer / --witness 在启动时直接 fail-fast（VACUUM INTO 快照复制是 SQLite 特性）；PG 上 HA 请交给 PostgreSQL 自己的流复制 / logical replication / PITR——那本来就是比文件级快照更强的机制。
  • 控制面随元数据后端走：SQLite 部署下 key/审计落 api_keys.db、视图定义落 meta/views/*.layout；PG 部署下两者全进 grovefs_control schema——一次 pg_dump 覆盖树+锁+控制面，没有本地要单独冷拷的控制面文件（control 套件实证；见 §13.2）。
  • 建表由服务端在 view 首次 M_OPEN 时幂等 CREATE SCHEMA IF NOT EXISTS + CREATE TABLE IF NOT EXISTS 完成，不需要预迁移脚本；根节点固定 id=1，setval(pg_get_serial_sequence(...), MAX(id)) 对齐序列，ROOT_INO 语义与 SQLite 完全一致。
  • 写并行（PG 独有，opt-in）：默认 SQLite 后端对同一 view 是单写者（一条权威连接 + 互斥锁）；换 --store postgres://… 后写路径改为至多 PG_WRITE_POOL_SIZE = 8 连接的 SERIALIZABLE 写连接池（HopsFS 路线，事务基座交给 PostgreSQL 自带 SSI）：不相交 (parent_id, name) 行上的并发写真正并行提交，读写重叠的一例由 SSI 中止并透明重试（200µs–25ms 指数退避、SERIALIZATION_MAX_ATTEMPTS = 12），SQLSTATE 40001/40P01 绝不外泄给 POSIX 调用方；rename 的环检查读、unlink 的引用计数 GC 读都并回同一事务。这是把「单权威写者」放宽为「单权威调度（serially equivalent）」，I1–I4 在任意 SSI 接受的调度下逐条不变。
  • 为什么没做 Redis：Redis 的 K/V+TTL 模型与视图树（rename/unlink/hardlink/refcount GC 需事务、锁需行级仲裁）不同构——把 relational 语义硬塞进 Redis 等于在应用层重做一个 PG，收益为负。GroveFS 只加 PG，不加 Redis。
由 test_pg.sh 19 个断言证明（拒绝 PG+HA 组合、单客户端 CRUD/rename/hardlink/symlink、docker exec psql 直接数 grovefs_v_<hex> 行数、跨客户端 mount A/B 收敛、hardlink unlink 跨端可见）；写并行另由 pg_ssi Rust 套件（5 项：distinct-parents 并行、同名竞争唯一胜出、并发 rename、hardlink 双名并发 unlink 仅一次 GC、混合 create+rename 收敛）与 pg_parallel bash 套件（三挂载 45 并发 create 墙钟远低于串行等效、同名并发 mkdir 恰一次成功且 node 表恰一行、无序列化错误外泄）端到端证明；无 PG 主机上均自动 SKIP，不拉低 GREEN。

模式命令行为
实时失效推送(默认,推荐)仅 --meta一客户端写成功后,meta-server 经事件总线向同用户其它订阅者广播失效(inval_entry+inval_inode),对端下次访问即时可见,无需轮询。

分布式 advisory 锁:flock / fcntl F_SETLK/F_GETLK 经 meta-server 的 locks 表(SQLite)集中仲裁,跨进程、跨机生效;主备切换后锁状态随快照复制存活。锁回收两条路径:①持锁进程崩溃——内核关 fd 触发 FUSE release(携带匹配 lock_owner),锁行即时删除,远小于 lease;②mount daemon 整机崩溃——无 release 也无续约,锁在一个短 lease(默认 15s)内过期被扫;存活持有者由 daemon 续约心跳(每 lease/3)持续续期,永不超时。非合作应用(cp/dd)仍不阻塞,与 NFS/SMB advisory 语义一致(由 test_locks.sh 段 4 崩溃即时回收 / 段 4b 续约跨过 lease 证明)。伸缩性边界：等锁在挂载进程里同步轮询(100ms 一次，上限 10 分钟)，会占住一个 FUSE worker 线程；默认 --threads 4 下同一挂载点 ~4 个进程同时等锁时，其他请求会排队——等锁多的场景调大 --threads，事件驱动唤醒在演进计划里。

8如何处理数据(重点)

8.1 物理布局

  • 单对象:blocks/<2hex>/<key>,一文件=一对象文件;对象按 key 哈希自动扇出进 256 个桶子目录,单层即止——单目录条目数不随总量增长,千万级对象下备份/遍历工具不退化;旧扁平存储自动回退可读,后台惰性收敛进桶,零人工迁移。
  • key 命名:写入时生成 UUID 作对象 key,存进视图 data_ref 字段。
  • 条带编码:data_ref = s<N>:<stripe_bytes>:<uuid>,第 i 块 key = {uuid}#{i},落在 servers[i % N]。无 s 前缀 = 旧单对象,天然向后兼容。

8.2 多 data-server 条带(聚合容量/带宽)

$Y mount --view alice \
     --data 10.0.0.5:50100,10.0.0.6:50100 --meta 10.0.0.5:50110 -m /mnt/alice
  • 文件 ≥ 16 MiB 才分块;小文件自然只落 chunk0(单节点)。
  • 条带读写内部复用分块并行 IO 原语。
  • 单地址 --data host:port 与旧行为完全一致。
诚实:条带的价值是把大文件摊到多节点的聚合容量。单条已饱和链路(loopback/单网卡)上实测无吞吐增益,须真独立链路才能测出收益——无实测数字不声称收益。

8.3 删除 / GC

unlink 后视图解除引用,后端据 key 尽力删全部分块;条带 remove 展开删所有 chunk,幂等(残留块可被 GC 清)。

跨视图共享对象的引用账本 refs：一个 data_ref 命名唯一一个底层对象，却可能被多个物理视图同时挂着名字（import 同一源文件进两个视图解析成同一 key、派生视图/别名共享基视图字节）。视图内引用计数看不见别的视图，单看它会误删他视图仍在引用的对象。故记账落在 <base>/meta/refs.db（PG 后端落共享表 grovefs_refs.holders）：每个视图 ATTACH 该账本，holder 计数与节点增删进同一个 IMMEDIATE 事务，跨文件原子提交。物理删除的准确规则是“该视图内此 key 的最后一个名字被摘除、且全局账本再无其它视图持有”——只有此时才 backend.remove。视图 db 被 out-of-band 删除（rm meta/x.db、新 --home）只会让账本高估、对象多留不误删；grovefs refs --db-path D rebuild 按现存视图树重算 holder 归位（SQLite 后端专用）。只有基视图（grovefs view create 显式创建的物理树）的删除才真正回收底层字节，派生视图/别名只读挂载、其删除从不物理 GC。无账本行的历史库退回“单视图”旧行为，既有部署不受影响。

8.4 备份与迁移

  • 数据对象:blocks/ 就是普通文件目录,可直接 rsync -a -H/文件系统快照备份。
  • 视图库:SQLite——本地模式 <home>/meta/<view>.db,meta-server 则在其 <db-path>/meta/ 下。勿在有写活动时裸拷 DB 文件;不能停机就 sqlite3 <db> ".backup"/VACUUM INTO 做一致性快照;HA 模式由 meta-server 用备份 API 复制(见 §9)。PG 后端时 backup_to_bytes 有意返回错误,交给 PG 自己的流复制/PITR。
  • 元数据不绑定硬件:node 行只存 data_ref(对象 key),对象路径 blocks/<FNV1a(key)%256 两hex>/<key> 是 key 的纯函数;没有绝对路径、设备号、主机名或宿主 inode。换机器/换系统只要把 blocks/ + meta/ 一起带走即可用(详见 §15.8.2)。按视图迁移的实测规模:5052 节点的视图 export 0.19s/1.16 MB、import 0.56s(含账本重建)，与数据量无关。
  • 拓扑边界(数据分布、非硬件绑定):多盘 --root 的数量与顺序要一致(或合并成单 root);条带 s<N>: 要保留 N 个 data-server 及顺序;整目录拷会把 HA epoch 带过去,旧主必须先停;PG 后端用 pg_dump/逻辑复制。

9高可用:meta-server 主备

两台 meta-server，各自一份 --db-path，靠快照复制保持一致：主写、备跟，主挂后自动提升、旧主回来自动降级。客户端只需多给一个 --meta 主,备 列表——不需要额外组件，也不需要 PG。

# 主:读写,并把快照周期推送给备
$Y meta-server --db-path /data/nodeA --listen 10.0.0.5:50110 --role primary --peer 10.0.0.6:50111
# 备:只读服务,主心跳丢失后自动提升为 primary
$Y meta-server --db-path /data/nodeB --listen 10.0.0.6:50111 --role standby --peer 10.0.0.5:50110
# 主(可选 RPO=0):加 --sync-repl,写返回前同步等备落盘 ACK
$Y meta-server --db-path /data/nodeA --listen 10.0.0.5:50110 --role primary --peer 10.0.0.6:50111 --sync-repl
# 真 fencing(opt-in):加 --witness <逗号分隔的 data-server 仲裁者列表,推荐奇数 N>,多数派授权把双写窗口收敛为有界(fail-safe)
$Y meta-server --db-path /data/nodeA --listen 10.0.0.5:50110 --role primary --peer 10.0.0.6:50111 --witness 10.0.0.7:50100,10.0.0.8:50100,10.0.0.9:50100
# 客户端故障转移列表:主挂自动切备继续读写
$Y mount --view alice \
     --meta 10.0.0.5:50110,10.0.0.6:50111 --data 10.0.0.5:50100 -m /mnt/alice

两节点怎么配

  • 两节点必须用各自独立的 --db-path(各存一份视图副本,节点间靠快照复制)。
  • primary 每 ~500ms 推快照 + 心跳 epoch;standby 心跳超时后提升并 epoch+1,旧主恢复发现更高 epoch 自动降级。
  • --sync-repl(opt-in,默认关闭):写 op 返回客户端前同步推快照并等备 fsync + 原子 rename 的 ACK,把 RPO 从 ~500ms 降到 0;代价为多一个控制通道 RTT + 一次 VACUUM INTO fsync。备不可达/超时时诚实降级为 async 并打 warn(不谎报 0)。由 test_ha.sh 段 7(RPO=0)/段 8(分区降级)证明。
  • --witness <addr[,addr...]>(opt-in,默认关闭):用主备都能访问的一个或多个共享 data-server 作独立仲裁者集合(逗号分隔,推荐奇数 N;N=1 即退化为单仲裁、行为与旧版完全一致)。权威需严格多数派 quorum_size(N)=N/2+1 个仲裁者同时授予——每个仲裁者都是下述相同的 Fence 租约节点,meta 侧对全列表并发 fan-out 并按多数派判决(witness_quorum)。
展开：租约怎么续、数据面怎么一起门控、以及部署前提
  • 为什么不会双主：多数派交叠保证正确:两个多数派集合必交于≥一个仲裁者,该仲裁者只把 token 顶高给第一个 claimer(第二个见 prev==我 只算续约不算顶高),故同值碰撞天然只有一主。每个仲裁者维护单调 fence token(OP_FENCE 的 fetch_max CAS 回传折入前的值 prev):claim 赢当且仅当 prev < 我的 epoch,prev >= 我 则被 fence(对端胜出或同值碰撞)——用 prev 而非折后 max 正是为了在仲裁者恢复时区分同值碰撞、绝不双主。在任 primary 每 tick 向多数派 续一份有界租约(lease,默认 3s)(多数报 prev>我则自降级);每个仲裁者拒绝重叠租约——同一时刻至多一份活租约,故多数活租约本身即独占权威的证明,写请求由本地租约有效性直接放行(不再每写一个仲裁 RTT,仅每续租一次,摊薄到整个窗口),被 fence 的过期主在租约到点后的下一次复证即拒绝;提升方亦非重叠——须待前任租约到期才可抢占(prev>=candidate 同值碰撞/对端更高,或前任租约尚活,则拒绝/延后,旧主可证明地已停)。数据面同遭门控:元数据面复证拦不住内容字节(write() 先落 backend、再 debounced touch meta),故客户端把其实时 epoch 贴到每个写意图数据帧(create/write/truncate/remove/fsync),作为 witness 的 data-server 对 epoch < token 的帧直接回 EROFS,过期主无法绕过元数据面静默写入内容;被封帧会向权威重取 epoch 并自动重试一次(自愈)。更关键的是 data-server 把「epoch 校验 + 落盘」与「仲裁 claim」用读写锁线性化(claim 取独占会等在途写排空),而 witness 与存储同在一节点,故过期写的字节不可能与新主写交叠——内容撕裂写在仲裁节点上被真正闭合(不再是“有界窗口”)。
  • 部署前提：该数据面门控只对被 quorum 顶高过 token 的 data-server（即 --witness 列表内的节点）生效，故须把 witness 与客户端实际写入的内容盘同节点部署；若内容盘在 witness 集合之外，它的 token 恒为 0、数据面 gate 不生效，仅剩元数据面 fence 兜底（不会双主，但少了内容层的第二道防线）。

配了 witness 之后：冻结写，而不是盲写

  • FAIL-SAFE:配置了 witness 却组不到租约多数派连续 >宽限(3s)时,节点放弃写权限——primary 自降级、standby 拒绝提升(写冻结,宁牺牲可用也不冒双写;瞬时仲裁错误不误伤单写,持续故障才由宽限兼底)。
  • 相比单仲裁的可用性提升:宕掉少数仲裁者仍能组多数续租、不冻结写,且少数仲裁者的 .fence_token 盘丢也不会复活过期主(多数仍保单调 token);唯失去多数才 fail-safe 冻结。每个仲裁者各自持久化 token 到 <root>/.fence_token,其重启不清零。由此双写窗口被租约安全余量(WITNESS_LEASE_SLACK=500ms)界定——对端只能在我方租约到点后取 token,而我方提前该余量停止信任本地缓存租约(而非 peer-only 的不封顶)。由 test_ha.sh 段 9（过期主重启被挡成 standby + token 持久化）、段 10（杀单 witness → 自降级 → 恢复后恰好一主）、段 11（3 仲裁者宕 1 仍续租不冻、宕 2 破多数才 fail-safe）证明。
诚实标注：
  • RPO：默认 async RPO ≈ 500ms，极端故障下最后 <500ms 的写可能丢失；加 --sync-repl 可降到 0。
  • 没有第三仲裁者就防不住脑裂：严格两节点、不配 --witness 时双写窗口不封顶（CAP 硬边界）；配了即 fail-safe——仲裁者多数派不可达时冻结写而非盲写/盲升，双写窗口收敛到租约安全余量内并保证收敛单主。
  • 代价：每续租一次向仲裁列表 fan-out；witness 须与内容盘同节点（见上）。（N=1 则退化为单仲裁旧行为）

Token 双面鉴权

中心 server 若裸监听 LAN,任何同网段主机都能按 key 读写对象/打开他人视图。加共享口令(同时覆盖数据面 OP_OPEN 与元数据面 M_OPEN):

$Y data-server     --listen 0.0.0.0:50100 --root /data/cluster --token s3cr3t
$Y meta-server --db-path ... --listen 0.0.0.0:50110 --token s3cr3t
$Y mount --view alice --data ... --meta ... --token s3cr3t -m /mnt/alice

token 不匹配 → 连接时直接 PermissionDenied,不重试。空 token(默认)= LAN-trusted 无鉴权,仅限可信内网。key 的视图绑定 / 只读（--view/--ro，见 §15.9.1）见 §6。

可撤销的 per-caller 凭据(API key 门)

token 是一份共享口令——拿到它的主机都能挂,也分不出“是谁挂的”,要踢一个调用方只能轮换 token 并断全部人。同一入口可改用 grovefs apikey 铸造的 key(--for mount 只开挂载/数据入口,只存 SHA-256、明文打印一次),逐调用方可审计、可撤销；再叠 --view V 可把 key 绑定单一视图（开其它视图握手即 E_AUTH 拒），--ro 则服务端逐写意图 op 强制只读（meta 面 E_NOTPERM、data 面内容写 EROFS）——这两个维度把“谁能碰哪棵树、读写还是只读”收进凭据本身在服务端逐 op 强制：

$Y apikey --db-path /data/cluster create --label client-a --for mount   # 明文只打印一次
$Y apikey --db-path /data/cluster create --label reader --for mount --view alice --ro   # 视图绑定 + 只读
$Y meta-server --db-path /data/cluster --listen 0.0.0.0:50110 --require-api-key
$Y data-server --listen 0.0.0.0:50100 --root /data/cluster --require-api-key --keys-from /data/cluster
$Y mount --view alice --data ... --meta ... --api-key '<id>:<secret>' -m /mnt/alice  # 或 export GROVEFS_API_KEY 使密钥不进 argv
$Y apikey --db-path /data/cluster calls --limit 20   # 每次挂载连接(含被拒)都归属到具体 key
$Y apikey --db-path /data/cluster revoke --id <id>   # 封停该 key 的活挂载(秒级)
$Y mount --view bob --data ... --meta ... --api-key '<reader key>'   # 绑定 alice 的 key 挂 bob
Error: ... "permission denied: this api key is bound to view 'alice', not 'bob'"   # 视图绑定 key 开其它视图即拒
$ mkdir <ro key 挂载点>/x   # --ro key 的挂载写一律被服务端拒，客户端据握手标志落内核只读
bash: ... Read-only file system

与 token 的两处关键差异：① 拒因逐字节随握手回客户端(缺失 key/未知 id/密文不符/格式不符(缺冒号)/scope 不符/已撤销各自成文),且服务端每秒复证活连接——撤销后该挂载在首个服务端往返上被打断、打印服务端原文并干净自卸载(不留下 Transport endpoint is not connected),其他 key 的挂载不受影响；② 挂载连接与治理调用同表可审计。--token 与 --require-api-key 可同时开(两道都得过)；不开时行为与不设门完全一致(仍落审计)。两面门都是 opt-in；data-server --keys-from 缺省取它的首个 --root(同机部署免参,分盘部署必须指对——指向空 key 库则 fail-closed、所有挂载被拒)。详细回显与诚实边界见 §15.9.1 与 USAGE.md §3.5.1/§6。

展开：读池 / 分页 / 遥测的取值与边界
  • 读池：SQLite 引擎 4 条附加连接（READ_POOL_SIZE = 4）按 WAL 读事务读已提交数据，自己的写立刻可见（reads_through_the_pool_observe_committed_writes 断言）；HA 备机/只读引擎不预开池，首次读懒建并归还。PgEngine 持对等的 PG_READ_POOL_SIZE = 4 只读池（取不到时回退写连接以如实暴露故障）；PG 写侧经 PG_WRITE_POOL_SIZE = 8 的 SERIALIZABLE 写池并行提交、SSI 冲突透明重试（见 §6.2）。
  • 分页：readdir_page(parent, offset, limit) 在 SQLite 与 PG 都下推成 LIMIT/OFFSET，FUSE 回调按 32→1024 几何块流式填缓冲；FUSE_DO_READDIRPLUS 与普通能力位分属不同的 all-or-nothing 组，内核不支持则自然回退。两者由 supports_paged_readdir() 门控：本地 SQLite/PG 与能分页的 meta-server 远端挂载（M_READDIRP 帧）都吃两者；LayoutMeta 派生/透镜与老服务端每缓冲取一次全量列表且不协商 PLUS（否则 PLUS 的胖记录会把全量重取次数乘 ~4 倍）。
  • 遥测：分段为 op_total / key 解析 / 后端 IO / 分片扇出 / 元数据 DB / 远程 RPC——是排障工具而非吞吐测量。关闭态每个埋点仅一次 relaxed 原子读即短路（连 Instant::now() 都不调用、不加锁、不分配），直方图按 worker 线程分片。开关 --stats / --stats-file <路径> / --stats-interval <秒> / env GROVEFS_STATS=1；只读控制节点 <mnt>/.grove-stats 仅在开启时出现（cat 即当前报告），退出时经 stderr 打印最终报告。端到端见 .build-bin/test_stats.sh；已知延后项：errno（失败 op）计数需扩 counter 注册表，本轮未做。

12.5 客户机:模板挂载单元(一个 view 一个实例)

mount 单元带 --foreground 保持进程附着(Type=exec 要盯住服务进程本体),内置 SIGTERM 处理:systemctl stop 会自动 fusermount -u 干净卸载,不留死挂载。

# /etc/systemd/system/grove-mount@.service —— %i = 视图名,挂载点 /mnt/%i
[Unit]
Description=GroveFS mount view %i
After=network-online.target
Wants=network-online.target
[Service]
EnvironmentFile=/etc/grovefs/grovefs.env
ExecStartPre=-/usr/bin/fusermount -u /mnt/%i   # 清掉上次异常退出的死挂载(- = 失败也继续)
ExecStart=/usr/local/bin/grovefs mount --view %i --foreground --data 10.0.0.5:50100 --meta 10.0.0.5:50110 --token ${GROVE_TOKEN} -m /mnt/%i
Restart=on-failure
RestartSec=2
[Install]
WantedBy=multi-user.target

# 拉起
sudo systemctl start grove-mount@alice          # 新 view 首挂即在中心按需建权威库,无需预先 init
findmnt -T /mnt/alice                           # 期望:grovefs:alice,FUSE
uid 两件事(见 §6.1):systemd 默认以 root 起挂载,上报 uid=0——无白名单约束时 root 放行即可访问;要其他用户也能访问挂点,加 --o allow_other 并在 /etc/fuse.conf 打开 user_allow_other。
改成逐调用方可撤销凭据（踢掉一台机不再需要轮换共享 token 并断全部人）：两个 server 的 ExecStart 各加 --require-api-key（data 侧另需 --keys-from 指到元数据根，若它不等于首个 --root），客户端把 --token ${GROVE_TOKEN} 换成 --api-key ${GROVE_API_KEY}，并用 grovefs apikey create --label <主机名> --for mount 铸造后写进同一份 root-owned 0600 的 grovefs.env（密钥因而进不了 ps 可见的 unit 文本）。撤销后的真实行为（实测）：该挂载在首个服务端往返上打印服务端拒因、干净自卸载并以退出码 0 结束——一次有意的收手而不是崩溃，所以 Restart=on-failure 不会重拉，unit 落 inactive (dead)（要辨“被踢”请看 journal 里那行拒因，或挂 OnFailure=/ExecStopPost= 告警）；拿被撤销的 key 重挂则 fail-fast。若希望被踢后自动重试（运维会重新铸一把），改用 Restart=always。其他主机的挂载全程不受波及。

12.8 HA 主备拓扑部署

要点:两台 meta-server 用各自独立的 --db-path(快照复制,不是共享盘!blocks/ 才是共享的,客户机 --data 始终指向同一组 data-server):

# nodeA(10.0.0.5):primary;nodeB(10.0.0.6):standby —— 同样写成 systemd unit,只改 --db-path/--listen/--role/--peer
$Y meta-server --db-path /data/nodeA --listen 10.0.0.5:50110 --role primary --peer 10.0.0.6:50111 --token $TOK
$Y meta-server --db-path /data/nodeB --listen 10.0.0.6:50111 --role standby --peer 10.0.0.5:50110 --token $TOK
# 客户端故障转移列表;
$Y mount --view alice --meta 10.0.0.5:50110,10.0.0.6:50111 --data 10.0.0.5:50100 --token $TOK -m /mnt/alice
防双写需第三方仲裁:把 3 个(奇数)data-server 写进 --witness,且它们应与客户端实际写入的内容盘同节点部署(数据面门控只对列表内 data-server 生效,见 §9)。验收:ssh nodeA systemctl stop grove-meta-server → nodeB 日志出现 meta HA: promoted to primary at epoch N,客户机继续可写;旧主回来自动降级为 standby。

13.3 恢复与节点修复三流程

  • 单机/本地模式:先 umount 停写(或停 meta-server),再 cp -a/rsync 整个 --home;恢复 = 拷回原位 → 重挂 → ls/cat 抽查。二进制不在备份范围——数据全在 --home。
  • SQLite + 自研 HA:备机坏了 → 修好后直接 systemctl start,它从主继续收 ~500ms 快照追平,无需手工灌数据;主机坏了 → 备自动提升,旧主修好 start 后见高 epoch 自动降级,配 --witness 时带旧快照重启也会被仲裁挡在 standby(test_ha.sh 段 9 证明)。两半全丢需重建:从归档快照恢复 <db-path>/meta/,且 epoch 重置的前提是所有 data-server 同时换新(否则残留 .fence_token 会挡住写——fail-safe 的正确行为,非损坏)。standby 的实时快照是复制体不是归档备份,仍建议定期对主/备任一侧做异地归档快照。
  • PostgreSQL 后端:视图树备份完全交给 PG 工具链(pg_dump/pg_basebackup + WAL 归档/PITR);GroveFS 侧只备 blocks/ + env 文件。--store 模式下自研快照备份 API 有意返回错误(设计如此)。

13.4 升级与滚动变更

  • 客户端二进制(单台无中断):systemctl stop grove-mount@alice → 替换 /usr/local/bin/grovefs → start。直接 kill 不行——死挂载要 fusermount -u 手工清。
  • 中心 server(无 HA):替换二进制 → systemctl restart grove-data-server grove-meta-server,接受秒级 IO 暂停。客户机挂载进程不需要跟着重启——远程链路对 server 重启透明(resilience 套件:连接池整体丢弃后有限退避重连)。
  • HA 滚动升级:先升级并拉起 standby → stop primary(≤3s PROMOTE_TIMEOUT 内备提升,客户端自动切地址)→ 升级旧主并以 standby 拉起(自动降级回初始形态)。混版未经验证,同一次大版本升级请中心与客户机保持同版。

data-server --listen0.0.0.0:50100缺省 127.0.0.1:50052 只接本机,要接客户端必须显式 0.0.0.0;端口自定,客户端 --data 指对即可

meta-server --db-path/data元数据根,视图库落 <db-path>/meta/;优先于全局 --home(后者仅兼容保留)
meta-server --listen0.0.0.0:50110同上(缺省 127.0.0.1:50053);元数据面单独占端口
两个 --tokenenv 那串分别把守 OP_OPEN/M_OPEN 两处握手;不带对 = 连接即 PermissionDenied,不重试
(可加 --require-api-key)—改按 per-caller API key 放行(grovefs apikey create --for mount 铸造)：拒因随握手回传、每次连接落审计、撤销能封停活挂载;data 侧另用 --keys-from 指到元数据根(默认取首个 --root)。见 §10/§15.9.1
(不传 --store)—这就是“用 sqlite3”:embedded SQLite,一 view 一 .db
(不传 --role/--peer/--witness)—单权威节点;宕机 = 元数据面暂停(盘上数据不丢);要 HA 按 §12.8 扩

两个前台窗口应各打一行 banner——data-server listening on 0.0.0.0:50100、meta-server listening on 0.0.0.0:50110 (base /data, role Primary);完整终端效果见 §14.13 实录①。

14.7 服务端硬只读：视图绑定 / 只读 API key（场景 C 上半）

# 存储机：两个角色各一把绑定 share 的 key，只给 A 读写
sudo grovefs apikey --db-path /data create --label A-rw --for mount --view share
sudo grovefs apikey --db-path /data create --label B-ro --for mount --view share --ro
sudo grovefs apikey --db-path /data list
# meta-server / data-server 都加 --require-api-key（data 侧 --keys-from 指到 /data）
# 两台客户端 ExecStart 换成下面两行全文后,各自 daemon-reload + restart
# A:/etc/systemd/system/grove-mount.service
ExecStart=/usr/local/bin/grovefs mount --view share --foreground --data 192.168.1.10:50100 --meta 192.168.1.10:50110 --api-key ${GROVE_A_KEY} -m /mnt/da
# B:(--ro key 已由服务端强制,客户端 --ro 留作双保险)
ExecStart=/usr/local/bin/grovefs mount --view share --foreground --data 192.168.1.10:50100 --meta 192.168.1.10:50110 --api-key ${GROVE_B_KEY} --ro -m /mnt/db
# 生效:
sudo systemctl daemon-reload && sudo systemctl restart grove-mount
参数意义
apikey create --for mount --view share [--ro]铸一把只能开 share 视图的挂载凭据;key 绑定视图后拿它开别的视图在 M_OPEN 处 E_AUTH 拒
--ro(key 侧)只读 key:读放行,每个写意图 op 服务端逐条动态重查回 E_NOTPERM→EPERM(data 面内容写 EROFS)——是鉴权拒绝不是故障;apikey revoke 对存活挂载即时生效
--api-key <ID:SECRET>(或 env GROVEFS_API_KEY)挂载时在 M_OPEN/OP_OPEN 呈递这把 key(env 让密钥不进 argv)。撤销即断开该挂载并使其自卸载,其他 key 不受波及;真准入靠这把 key

14.8 权限三档 + 撤销演练（场景 C）

三档由弱到强，选一档就够，不需要叠满：

档位服务端怎么开客户端怎么连能拦住什么
1 · 共享 token两服务加 --token $TOK--token $TOK没有口令的主机；分不出谁是谁，踢人只能轮换口令
2 · API key两服务加 --require-api-key（data 侧 --keys-from /data）--api-key ID:SECRET逐调用方可撤销、可审计；仍可开任意视图
3 · 绑定 + 只读第 2 档 + 铸 key 时加 --view share / --ro同第 2 档开别的视图握手即拒；只读 key 的写逐 op 被拒
先看顺序：先开服务端门、再铸 key、最后换客户端；反过来会让已有挂载在重启后因无 key 而连不上。
  1. 服务端开门（存储机） 
    # meta 侧：卡 M_OPEN
ExecStart=/usr/local/bin/grovefs meta-server --db-path /data --listen 0.0.0.0:50110 --require-api-key
# data 侧：卡 OP_OPEN；--keys-from 指向元数据根（不等于首个 --root 时必须显式写）
ExecStart=/usr/local/bin/grovefs data-server --listen 0.0.0.0:50100 --root /data --require-api-key --keys-from /data
# 改完：
sudo systemctl daemon-reload && sudo systemctl restart grove-meta-server grove-data-server
  2. 铸两把 key（只需一次，明文只打印这一次） 
    sudo grovefs apikey --db-path /data create --label A-rw --for mount --view share
sudo grovefs apikey --db-path /data create --label B-ro --for mount --view share --ro
# 期望：apikey created — shown ONCE ... key: <id>:<secret>
sudo grovefs apikey --db-path /data list   # 核对 scope=mount / view=share / rw 列
  3. 把 key 写进 env 并切客户端（两台） 
    # /etc/grovefs/grovefs.env（root 0600，与 token 同一份文件）
GROVE_A_KEY=<id>:<secret>
GROVE_B_KEY=<id>:<secret>
# 两台 unit 的 ExecStart 把 --token ${GROVE_TOKEN} 换成 --api-key ${GROVE_A_KEY} / ${GROVE_B_KEY}
sudo systemctl daemon-reload && sudo systemctl restart grove-mount

    为何走 env：密钥不进 ps 可见的 unit 文本；--api-key 也可由客户端进程的 GROVEFS_API_KEY 提供。

  4. 验证三件事 
    # ① 读写 key：写成功
sudo sh -c 'echo ok > /mnt/da/a.txt' && sudo cat /mnt/db/a.txt
# ② 绑定的 key 开别的视图 → E_AUTH（在服务端握手处就被拒）
grovefs mount --view other -m /mnt/x --data 192.168.1.10:50100 --meta 192.168.1.10:50110 --api-key "$GROVE_A_KEY"
# 期望：this api key is bound to view 'share', not 'other'
# ③ 只读 key 的挂载写 → 权限拒绝（EPERM，不是磁盘故障）
sudo touch /mnt/db/y
# 期望：Permission denied
  5. 看审计（每次连接、含被拒的都有一行） 
    sudo grovefs apikey --db-path /data calls --limit 8
# ts | key_id | method(meta/data) | tool(M_OPEN/OP_OPEN) | ok | detail(view='share' uid=1005)
  6. 撤销一把 key（权限管理的闭环） 
    sudo grovefs apikey --db-path /data revoke --id <A-rw 的 id>
# 期望：apikey: revoked id='…' (label 'A-rw'); past calls keep attribution
# A 机上再写一次：
sudo sh -c 'echo late > /mnt/da/late.txt'
# 期望：权限不够（EACCES）；接下来挂载会自卸载
tail -2 /tmp/grovefs-mount-*.log
# 期望：access refused by the server (… has been revoked) — unmounting this view
findmnt -T /mnt/da; systemctl status grove-mount | head -3
# 期望：无挂载；inactive (dead) — 退出码 0，Restart=on-failure 不会重拉
  7. 拿被撤销的 key 重挂（应 fail-fast） 
    grovefs mount --view share -m /mnt/x --data … --meta … --api-key "$GROVE_A_KEY"
# 期望：authentication failed: this api key has been revoked
这一步最常见的四个坑
  • 全部挂载突然被拒：data-server --keys-from 指到了空库或错目录 → fail-closed（这是设计）。核对它与 meta-server --db-path 是同一个根。
  • 撤销后 systemd 不重拉：预期行为（干净收手、退出码 0）。想自动重试改成 Restart=always；要报警就挂 OnFailure=。
  • 只读角色用不了 flock：加锁类 op 归为写意图，只读 key 一律拒；需要共享锁做读协调就用一把读写 key。
  • 撤销没有“立即”生效：复证是 op 驱动的，边界是“撤销后的首个服务端往返”；纯内核缓存命中的读不会被打断。

14.9 换成 PostgreSQL（场景 D）

目标：客户端命令一个字不改，把元数据树与控制面从本地 SQLite 换成 PG。这是二选一，不是叠加——同一棵权威树只落一种后端。

  1. 准备库与权限（PG 主机 192.168.1.20） 
    sudo -u postgres createdb grovefs
sudo -u postgres psql -c "CREATE ROLE grove LOGIN PASSWORD 'pw';"
sudo -u postgres psql -c "GRANT CREATE, CONNECT ON DATABASE grovefs TO grove;"
# 不需要预建表：视图首次 M_OPEN 时服务端幂等 CREATE SCHEMA/TABLE
  2. 改 meta-server 的启动行（只改这一处） 
    sudo systemctl stop grove-meta-server
# unit 里加一行参数（--role/--peer/--witness 不能同时出现，否则启动即退）
ExecStart=/usr/local/bin/grovefs meta-server --db-path /data --listen 0.0.0.0:50110 \
     --store postgres://grove:pw@192.168.1.20:5432/grovefs --require-api-key
sudo systemctl daemon-reload && sudo systemctl start grove-meta-server
journalctl -u grove-meta-server -n 5   # 期望：正常 listening，无 schema 相关报错
  3. 控制面命令接同一 URI（否则它们还在改本地文件） 
    # 三个命令都要加 --store（或用 env GROVEFS_STORE 统一给）
export GROVEFS_STORE='postgres://grove:pw@192.168.1.20:5432/grovefs'
sudo -E grovefs apikey --db-path /data create --label A-rw --for mount --view share
sudo -E grovefs view --db-path /data list
# data-server 的 key 门也要跟着走：加 --store 后 --keys-from 不再使用
ExecStart=/usr/local/bin/grovefs data-server --listen 0.0.0.0:50100 --root /data \
     --require-api-key --store postgres://grove:pw@192.168.1.20:5432/grovefs
  4. 验证：树、锁、控制面都在 PG，本地不再长控制面文件 
    psql "postgres://grove:pw@192.168.1.20:5432/grovefs" -c '\dn grovefs_v_*'
# 期望：grovefs_v_7368617265（share 的 hex）等，一视图一 schema
psql "postgres://grove:pw@192.168.1.20:5432/grovefs" -c '\dt grovefs_control.*'
# 期望：api_keys / mcp_calls / view_defs 三张表
ls /data/meta  # 期望：只剩切库前的旧 .db；新建视图不再生成 .db/.layout/api_keys.db
findmnt -T /mnt/da   # 客户端侧：命令未变，仍正常挂载
  5. 备份口径跟着变 
    pg_dump --format=custom "postgres://grove:pw@192.168.1.20:5432/grovefs" > grovefs.dump
rsync -a -H /data/blocks/ /backup/blocks/   # 字节仍在文件系统，单独备

    一次 pg_dump 覆盖视图树 + 锁 + 控制面；高可用交给 PG 流复制 / PITR（与自研 --role/--peer/--witness 互斥）。

换库时必须知道的四件事
  • 旧 SQLite 视图不会自动搬进 PG：切库后新建/首挂的视图才落 PG schema；要保留旧树就挂载旧库再 rsync 到 PG 视图，或重建。
  • fork 在 PG 上未实现：view fork 会明确拒绝（树拷贝需要 SQLite 文件级快照路径）；派生 / 别名 / MCP 治理均可用。
  • view export/import 面向本地 SQLite 树：PG 侧迁移用 pg_dump / 逻辑复制。
  • 控制面命令漏加 --store 会“双写两处”：它们会去改本地 meta/views/*.layout 与 api_keys.db，而服务端读 PG——表现为“改了不生效”。统一导出 GROVEFS_STORE 最稳。

14.10 主备切换演练（场景 E，可选）

  1. 两台 meta-server，各自的 db-path（不共享盘） 
    # nodeA 192.168.1.10
grovefs meta-server --db-path /data/nodeA --listen 192.168.1.10:50110 --role primary --peer 192.168.1.13:50110 --token "$TOK"
# nodeB 192.168.1.13
grovefs meta-server --db-path /data/nodeB --listen 192.168.1.13:50110 --role standby --peer 192.168.1.10:50110 --token "$TOK"

    两台都写成 systemd unit；--db-path 必须是各自独立的目录（节点间靠快照复制同步）。

  2. 客户端写故障转移列表 
    grovefs mount --view share -m /mnt/da \
     --data 192.168.1.10:50100 --meta 192.168.1.10:50110,192.168.1.13:50110 --token "$TOK"
  3. 演练：停机 → 提升 → 回切 
    sudo sh -c 'echo before > /mnt/da/t.txt'
sudo systemctl stop grove-meta-server          # 在 nodeA 上
journalctl -u grove-meta-server -n 3           # nodeB：meta HA: promoted to primary at epoch N
sudo sh -c 'echo after > /mnt/da/t.txt'        # 期望：客户端自动切到 nodeB，继续可写
# nodeA 修好后再起：日志出现 demoted to standby，自动回到从属
  4. 要 RPO=0 或防脑裂再加参数 
    # RPO=0：写返回前同步等备机落盘（代价：多一次 RTT）
... --role primary --peer 192.168.1.13:50110 --sync-repl
# 防脑裂：3 个（奇数）仲裁 data-server，需多数派授予
... --role primary --peer 192.168.1.13:50110 --witness 192.168.1.10:50100,192.168.1.11:50100,192.168.1.13:50100
如实标注：默认 async 的 RPO ≈ 500ms；严格两节点且不配 --witness 时无法防脑裂（CAP 硬边界）。配了 witness 就 fail-safe：仲裁多数派不可达时冻结写，恢复后自动解冻。细节见 §9。

14.11 日常运维三件事（场景 F）

每天 1 分钟巡检、每周一次备份、每次升级后跑回归。完整故障表见 §13。

  1. 巡检（存储机 + 客户端各跑一遍） 
    systemctl is-active grove-data-server grove-meta-server
findmnt -t fuse | grep grovefs
ss -lntp | grep -E '50100|50110'
du -sh /data/blocks; df -h /data
journalctl -u grove-meta-server --since yesterday | grep -E 'promoted|demoted|fenced|fail-safe'

    健康 = 进程 active + 端口在听 + 挂载在位 + 日志没有新增的 promoted/fenced 行。

  2. 备份（SQLite 部署）

# 不能停机时：sqlite3 /data/meta/share.db ".backup /backup/share.db"（或 VACUUM INTO）

sudo systemctl start grove-meta-server

    PG 部署只备两样：pg_dump + blocks/（见 14.9）。/etc/grovefs/grovefs.env 里的 token 单独加密保管。

15.0 视图三问速览:怎么定制 / 元数据存哪 / 权限怎么管

① 如何定制视图:规则透镜,只改呈现不搬字节

定制的唯一素材是基视图的真实显示路径(先查再写:挂载后 find,或 MCP list_view_tree 不挂载只读元数据渲染;不要照源目录结构猜——import 会把源目录整体挂进 /seeds 类前缀下)。规则一行一个动词(# 注释):hide <src> 剪子树、only <src> 白名单、map <src> <dst> 把条目搬到虚拟显示路径(父目录自动合成)、link <src> <dst> 同一批条目再加一个名字。四个入口共用同一副 LayoutMeta 透镜,只差规则从哪来:

入口规则来源生效范围写语义
mount --layout F客户端本地文件只影响这个挂载全树可写,写落真实条目
grovefs view define服务端 meta/views/D.layout所有挂 --view D 的客户端派生挂载只读,写回基视图
grovefs view fork独立元数据树 meta/X.db单独一棵可组织的树结构可写、内容 EROFS、字节共享
grovefs view aliasalias <R> 一行公开名 1:1 治理全树可写,真实名拒挂

定制出的形状可以和基视图完全不一样:<src> 端被基树钉死,<dst> 端随你发明;想让自定义树成为视图全貌,配一条 only <新树根>。透镜做不到的只有凭空造内容——每个渲染条目都是基树条目的换名/镜像/裁剪加合成目录,字节永不复制。热生效:经 meta-server 的挂载 ≤2s 自动换形,本地 --home 裸挂载挂载时解析一次。详章 §15.5–§15.8.1、MCP 面 §15.9 与 skills/grovefs-mcp/。

② 视图元数据如何存储:一 view 一引擎,控制面跟随后端

<db-path>/
├─ blocks/<2hex>/<key>   内容字节:key=UUID,按哈希自动扇出 256 桶,单目录条目不随总量增长
└─ meta/
   ├─ <view>.db          每物理视图一棵权威树(SQLite WAL):
   │   node(id/ino, parent_id, name, is_dir, data_ref, link_target,
   │   mode/uid/gid, mtime/atime/ctime, UNIQUE(parent_id,name)) + ctrl + locks(锁租约)
   ├─ refs.db             跨视图共享对象持有者账本(GC 判「最后一个名字」的唯一依据)
   ├─ views/*.layout      派生/别名/fork 定义(派生=首行 base <B>+规则行;别名=单行 alias <R>;fork=单行 fork <B>)
   └─ api_keys.db         API key SHA-256 摘要 + 调用审计(SQLite 后端的控制面;PG 后端进 grovefs_control)

名字解析链:mount --view X → M_OPEN(X) → 服务端查 meta/views/X.layout——首行 base(派生)则打开其基物理树并套上透镜、只读挂载;首行 alias 则直接落到真实树的同名入口、全树可写且真实名拒挂;首行 fork 则打开它自己的 meta/X.db;无定义则 X 就是物理视图。树与字节各走一半:data_ref 是两者唯一连接点(条带对象编码 s<N>:<stripe>:<uuid>)。SQLite 与 PG(grovefs_v_<hex(view)> 一 view 一 schema + 共享表 grovefs_refs.holders)是二选一替代;控制面同样跟随后端——--store postgres://… 下视图定义/key/审计全进 grovefs_control schema(view_defs/api_keys/mcp_calls),本地不落任何控制面文件(control 套件实证)。详章 §8.1 物理布局 / §8.3 删除与账本 / §8.4 备份清单 / §6.2 后端选型;USAGE §5.0 一屏解剖。

③ 权限如何管理:两层栈 + 一把可撤销的钥匙

层机制谁强制粒度与语义
1token(共享口令)服务端握手集群准入,不匹配 E_AUTH;客户端自报 uid 属 advisory,不参与准入
2--view 名服务端路由树选择,不是身份:任何 uid 挂同名 view 即落同一棵树
3API key(--require-api-key)服务端逐 op逐调用方:scope 分平面(mcp|mount|any)、--view V 绑定拒开它树、--ro 拒写(meta 面 E_NOTPERM/data 面 EROFS/锁 EPERM)、可撤销(活挂载 ≤1s 封停)、全量审计
✗显示治理(派生/别名/fork)——不是安全边界:只改呈现,可见即可读、可读即可写回(fork 内容除外)

M_OPEN/OP_OPEN 按序过门:① token → ② key 门(scope/撤销/绑定) → ③ ro 写门 → ④ view 名→引擎缓存。治理面 grovefs mcp --require-api-key 共用同一份注册表(SQLite:api_keys.db;PG:grovefs_control.api_keys;MCP 加 --store 即接 PG),tools/call/resources/read 全部落审计。详章 §6 共享视图与权限模型 / §10 鉴权 / §15.9.1 key 门与审计;USAGE §3.5.1 十步演练、§6.1 绑定/只读实测。

15.2 存量大量数据进来:两条正路,首选零拷贝 grovefs import

# 首选：在存储机一条命令登记整棵已存在的目录树（不读内容、不占额外盘）
grovefs import --db-path /data/cluster --view legacy --source /data/legacy --prefix /legacy
# 备选：在任一台已挂载客户端分批灌入（层级随写自动成型）
rsync -a /srv/legacy/ /mnt/da/imported/
# ≥4MiB 写自动分片并发；多地址且 ≥16MiB 自动条带——导入无需特殊调优
ls /data/blocks | head && find /mnt/da/imported -maxdepth 2 | head   # 抽验

取舍：import 零拷贝但导入对象是单文件（不走条带）、向在线挂载靠 TTL 收敛；rsync 灌入多一份字节但可条带、即时推送。经 FUSE 写入的吞吐上限在帧链路与中心盘，TB 级存量低峰分批；百万级文件会让 view.db 相应增长，属正常。

15.3 客户端“显示方式”的机制一览

机制效果适用
不同 --view = 不同树完全独立层级，互不可见A/B 看根本不同的东西
同 --view = 同一棵树字节一份，所有挂载点同一棵权威树(实时同步)；B 只读用 --ro/只读 keyA/B 共享同一批数据
mount --layout 显示透镜(§15.5)同一棵树，每个挂载点自行 hide/only/map/link：部分显示、重组路径，字节不动定制显示形状，不需两份数据
服务端派生视图(§15.6)同一套透镜规则命名后集中存在服务端(meta/views/)，客户端只 mount --view <派生名>：同名跨机同形、可按名配只读 key；派生(虚拟)视图挂载一律只读(写走基名)团队共享显示契约、免分发规则文件；只读分发形状
服务端纯别名(§15.8)公开名 1:1 映射物理视图(alias <真实名>，无规则)：别名挂载全树可写，真实名从此不是挂载入口(猜出来也挂不进)名字治理：对外名自由轮换、存储身份不外露(泄露时 --retire 一条命令原子轮换：旧名失效、真实名全程拒挂)；与形状治理(派生)正交互补
服务端 fork 视图(§15.8.1)把基视图的目录项复制成独立元数据树(meta/<名>.db，保留 inode/硬链接)，内容字节共享不拷贝：结构可写(mkdir/rename/unlink/chmod…)，内容写 EROFS(不上传)，删名字只影响本视图需要一个可自由整理、但不伤基视图的副本树(实验分组、归档整理)；比“拆两个 view 灌两遍”省字节
树内多入口：硬链+软链同一份字节摆出多种组织(按年/按类/快捷入口)同 view 内多视图目录
单视图元数据导出/导入(§15.8.2)把一棵视图树写成宿主无关的 JSONL(id/inode/硬链接/权限/属主/时间全保留，不含字节)，在另一个存储根重建并原子安装；字节另拷 blocks/换机器/换系统/换目录迁移，或只搬其中一棵基视图；实测 5052 节点导出 0.19s、导入 0.56s
cd /mnt/da
mkdir -p by_year/2026 by_type/docs
ln imported/report.pdf by_year/2026/report.pdf   # 硬链接：两个名字指同一对象，字节只存一份
ln -s by_year recent                              # 软链接：目录快捷入口(只是路径字符串)
rm imported/report.pdf                             # 安全：硬链接还在，对象不会被删

GC 语义(源码保证)：对象只在最后一个引用它的目录项消失时才删；refcount 读写同一事务，并发硬链不误删不泄漏。软链接不占引用，真删目标后悬空；不要拿软链接指另一个 view 的路径(另一棵树在该挂载点根本不可见)。

15.4 “B 只想看到一部分”：现有三条路 + 未实现清单

  1. mount --layout 显示透镜(§15.5)，或其服务端集中定义版——派生视图(§15.6)：B 的挂载加 only /by_public 或 hide /photos/private(本地规则)，或由管理员 grovefs view define 后 B 直接 mount --view <派生名>(免分发规则文件、可按名配只读 key)——字节零复制、其它挂载无感；但两者都是显示定制不是硬安全边界(B 不带透镜/直挂基名仍见全树，拦住他的是 token / key)。区别在写权限：派生(虚拟)视图挂载一律只读(形状由服务端治理，写只能走基名)，而客户端自备的 --layout 透镜仍可写(直写真实条目)——B 需要可写形状就用 --layout，只要只读分发形状就用派生视图。
  2. 同 view + 目录约定：B 只进 by_public/ 这类发布目录——简单，但约定不是强制(B 能 cd 到任何地方)。
  3. 拆两个 view + 灌两遍：share_pub 只放可公开内容(rsync --include/--exclude 筛)，B 挂它配只读 key——硬隔离真只读，代价是公开部分字节多一份。要真安全隔离选这条。

未实现(诚实标注)：子树挂载 --subpath/--prefix(--layout only/hide 是显示裁剪，不是路径 chroot)；跨 view 硬链接(link 只在树内；跨视图共享字节用 fork 视图——独立元数据树、内容共享，§15.8.1)；导入后源目录的持续自动同步(watcher/定时重扫)——grovefs import 是手动幂等增量命令；per-directory 强制权限（现有机制的粒度是 view × 调用方凭据；--layout 可做目录级显示裁剪但不构成强制隔离）。

15.8 纯别名：名字治理：grovefs view alias

§15.6 的派生视图治理“长什么样”；纯别名治理“叫什么”：名字就是别名，映射值才是真实名。定义同放 <db-path>/meta/views/<name>.layout（PG 后端落 grovefs_control.view_defs），首行 alias <真实视图>、不带任何规则行。与派生视图恰成正反两面：别名挂载全树可写(它就是真实视图的原形)，而真实名从此不是挂载入口——本地(--home)与 meta-server 都拒挂被治理的真实名：公开名与存储身份解耦，对外名字可自由轮换，猜出真实名也挂不进来：

命令参数释义效果

15.8.1 fork 视图：独立元数据树，结构可写、内容只读：grovefs view fork

命令参数释义效果

15.8.2 单视图元数据导出/导入：换机器、换系统迁移：grovefs view export / import

GroveFS 的元数据不绑定硬件：node 行只存 data_ref(对象 key)，对象路径 blocks/<FNV1a(key)%256 两hex>/<key> 是 key 的纯函数；没有绝对路径、设备号、主机名或宿主 inode，GroveFS 自己的 ino 也在 DB 里。所以整库搬到另一台机器可直接用——前提是元数据与内容字节一起走。按视图、跨机器、可选择性迁移时用 view export / view import：

命令参数释义效果

导入是原子的：先在 D/meta/.V.import-<pid>-<时间> 建临时树，全部行与校验通过、WAL 合并后才 rename 到 D/meta/V.db——坏文件/悬挂父节点/计数不符/失败的 --replace 都不会破坏旧树。守卫：输出已存在需 --force；目标已有定义槽先 view rm；表头 format/version 不符、根不是 id=1 的目录、悬挂父节点、表头计数与正文不符均整单拒绝；--as-fork 要求基视图在目标机已存在且本身无定义。

迁移的拓扑约束(数据分布，不是硬件绑定)：多盘 --root 的数量与顺序要一致(或合并成单 root)；条带 s<N>: 要保留 N 个 data-server 及顺序(否则明确拒绝)；整目录拷会把 HA epoch 带过去，旧主必须先停(export/import 与 fork 有意不复制 ctrl/locks)；PG 后端用 pg_dump/逻辑复制，view export/import 目前面向本地 SQLite 树；整目录冷拷不能裸拷运行中的 SQLite(WAL)，用停写或 .backup/VACUUM INTO。多个基视图：可建任意多个基视图(init --view A/view create --view A)，各自一棵 meta/A.db，树/字节/权限/删除互不影响，view list 全部列出；迁移可按视图进行，key 也可按视图分别绑定。回归：migrate 套件 74 条断言(挂载中导出/宿主无关性/虚拟名与覆盖守卫/跨绝对路径导入/硬链接与权限保真/原子替换/损坏输入拒绝/--as-fork 账本共享/多基视图独立)。

规模实测(单机、默认 IO，bash .build-bin/perf_migrate_scale.sh 可复跑)：迁移一棵 5052 节点、含 5000 个对象的视图——export 0.19s 产出 1.16 MB JSONL(视图库文件的 1.16 倍，约 230 B/节点)；import 到另一个绝对路径的存储根 0.56s(含跨视图账本重建)；挂载后 0.23s 枚举完 5000 个文件，内容逐字节一致、权限与属主保留。同一批文件当初注册进源视图(零拷贝导入)花了 83s——逐对象的存储开销完全不在导出/导入路径上。迁移代价由命名空间大小决定，不由数据量决定；字节那一半另走 rsync -a -H blocks/。

15.9 智能体定制数据列表：MCP 接口：grovefs mcp

§15.6/§15.8/§15.8.1 的视图治理同时是一套 MCP(Model Context Protocol)工具：grovefs mcp 在 stdio 上说换行分隔的 JSON-RPC 2.0(实现 2025-06-18 协议的常用方法面：生命周期 initialize/ping、工具 tools/list/tools/call、资源 resources/list/resources/templates/list/resources/read、提示 prompts/list/prompts/get、补全 completion/complete、日志 logging/setLevel 与服务端 notifications/message；客户端通知一律静默不作答)，任何 MCP 客户端(Claude Desktop、IDE 智能体等)把它当子进程拉起，智能体即可通过接口自动定制数据列表的形状——查视图、探查某视图真实呈现的目录清单并按绝对显示路径写规则(list_view_tree 经已发布透镜渲染、还能不落盘预览一副待发布规则的形状，get_view 读回单个定义原文)、用内联规则文本发布只读派生透镜、轮换公开名、删定义、发布前把整副定义走完全部治理守卫做干跑校验(validate_definition，不写盘)；规则以文本随行(hide/only/map/link，同 --layout 四动词)，智能体不需要碰任何文件。九个工具与 grovefs view 子命令共用同一套库函数(grovefs::mcp)：一个契约、两个入口，校验/拒绝文案/落盘动作逐字节相同，智能体做不出 CLI 做不出的事，也绕不过任何守卫。

15.9.1 给接口和挂载点上把锁：API key 认证、scope 分区与调用审计(grovefs apikey)

同一个服务常常要面对多个不同调用方——智能体把一个 grovefs mcp front 出去,多台客户机经 LAN 挂同一个 meta-server——此时需要可撤销的凭据与归属审计。grovefs apikey 铸造 API key(只存 SHA-256 摘要,明文仅在 create 时打印一次,故 api_keys.db 泄露也换不出可用凭据),并给每个 key 打 scope：--for mcp(只开治理接口)、--for mount(只开 --require-api-key 的 meta/data 服务端)、--for any(默认,两者皆可;scope 出现前铸造的旧 key 全是这一档,故老部署无需改动)。两处入口共用同一份注册表（SQLite 部署：<db-path>/meta/api_keys.db；PG 部署：grovefs_control.api_keys），靠 scope 隔离：挂载凭据重放不到治理 API,智能体 key 也开不了数据面。

挂载 key 的两个访问维度

挂载 key 还可带两个访问控制维度：--view V 把凭据绑定单一物理视图 V(开别的视图握手处即 E_AUTH 拒;省略则系统级 key 可开任意视图)；--ro 标为只读(服务端 meta 面逐写意图 op 拒 E_NOTPERM、data 面内容写拒 EROFS，并在 M_OPEN 回包提示客户端只读挂载)。

三处入口：治理面 / 挂载面 / 审计面

治理面：grovefs mcp --require-api-key 对所有读写治理状态的方法设门——tools/list、tools/call、resources/list、resources/templates/list、resources/read、completion/complete(initialize / ping / prompts/* / logging/* 始终开放,好让客户端完成握手并出示 key)。挂载面：meta-server --require-api-key 卡 M_OPEN、data-server --require-api-key 卡 OP_OPEN(--keys-from 指到元数据根,默认取首个 --root),客户端以 mount --api-key <ID:SECRET> 呈现(或导出 GROVEFS_API_KEY 使密钥不进 argv)。

审计面：每一次 tools/call、resources/read 与每一次挂载连接(含被拒的)都追加进同一张表(时间、key、平面 method、工具 tool、成败、详情),grovefs apikey calls 回读。撤销只是把行标记为 revoked(历史调用仍保留归属),撤销后的 key 立即鉴不上,且已建立的挂载也被封停。控制面状态跟随元数据后端：SQLite 部署落 api_keys.db，PG 部署与视图定义一起进 grovefs_control（grovefs apikey/mcp 加 --store 或 env GROVEFS_STORE 接同一 URI）。

四个子命令

四个子命令：create --label L [--for any|mcp|mount] [--view V] [--ro] / list [--view V](含 view/rw 列；带 --view 时只列能开该视图的 key，纯别名也匹配绑定到真实名的 key) / revoke --id ID(支持精确 id 或唯一前缀) / calls --limit N(默认 20,倒序)。无法自定义握手的客户端,可由运维方导出 GROVEFS_MCP_API_KEY='<id>:<secret>' 预鉴权整个治理服务进程(挂载侧对应 GROVEFS_API_KEY)。

诚实边界与回归

诚实边界：这把 key 认证的是入口的调用方——它让某个调用方能(或不能)发治理写命令、能(或不能)开某棵视图树,并把每次准入归咎到具体 key,但不改变治理语义本身；视图绑定/只读维度由服务端逐 op 强制(§6.1)；活连接复证是 op 驱动的(有流量才查),故封停边界是“撤销后的首个服务端往返”——完全由内核缓存回答的读不需要往返,因此不会被打断(下一次往返即封)；--token 与 --require-api-key 可同时存在,两道都得过。不开 --require-api-key 时,服务行为与不设门完全一致(只是照样落审计)。回归：apikey 套件(26 条断言：铸造/列表/哈希不落盘/无 key 拒·错 secret 拒·对 key 放行/调用归属/撤销即失效且行保留/短 id 前缀撤销/env 预鉴权/默认不设门回归)与 mountkey 套件(64 条断言：scope 铸造与 typo 拒绝/六类拒因入协议/准入与 env 回退(argv 不泄密)/连接审计到具体 key 与视图/scope 双向隔离/撤销封停活挂载且无脏 endpoint/其他 key 不受波及/token 与 key 双门 AND/数据面独立门/故障转移携带凭据/不设门默认路径无回归/视图绑定 key 跨视图拒挂与审计归属/只读 key 服务端强制写拒)。下列回显取自真实运行：

17诚实标注的边界

以下为本项目遵循“工程诚信”原则明确标注的限制，而非隐藏假设。每一条都对应代码里的实现或明确的未实现项。

传输、HA 与验证

  • 传输协议:当前为自定义 TCP 帧,非 gRPC。gRPC(tonic/prost)已做 go/no-go 闸门评估,结论 GO(tonic 0.14 免 protoc),但完整集成有意延后——独立可弃的末位项,现协议已正确且被测。
  • HA:RPO ≈ 500ms（async；--sync-repl 可降到 0）。真 fencing 依赖第三方仲裁：--witness 取 N 个共享 data-server 作多数派仲裁（需 N/2+1 授予），已落地并 fail-safe——仲裁者多数派不可达时冻结写而非盲升；primary 持不重叠的有界租约、对内容数据帧按 token 门控，双写窗口收敛到租约安全余量内；宕少数仲裁者仍不冻写、少数盘丢不复活过期主（N=1 退化为单仲裁）。仅严格两节点不配 witness 时仍无法防脑裂、窗口不封顶（CAP 硬边界）。详见 §9。
  • 条带:单条饱和链路无吞吐增益,价值在多节点聚合容量;真实多机链路须重测后才可声称收益。
  • 验证环境:全部在 127.0.0.1 回环(模拟 LAN)验证,尚未做真实多机与 fio 级基准。

权限与身份

  • uid 归属:客户端上报 uid 属 advisory(TCP 客户端可伪造或 --as-uid 覆盖),只作为条目属主记进锁仲裁与审计,从不作为访问控制门;集群准入由 --token（或开了 --require-api-key 时的活 API key）把关,「谁能碰哪棵树、读写还是只读」由 key 的 --view/--ro 绑定在服务端逐 op 强制。只读 key 连 flock/共享锁也会被拒(锁 op 归写意图)。

显示与视图治理

  • 显示透镜 --layout:是显示层定制而非安全边界——绕过透镜直接挂同一 view 仍见全树,硬隔离用独立 view + token / 视图绑定 key;向纯合成目录创建/重命名进入返回 EPERM、撞透镜已显示名返回 EEXIST、only 模式白名单外不可写;symlink 目标文本不改写;共享 meta-server 下合成目录条目失效推送可能不命中透镜坐标(建议 --strict);规则限同一 view 内部重排,不支持跨 view 引用。
  • 服务端派生视图 grovefs view：一律只读挂载（硬契约）——形状集中治理、只分发不修改，写只属于基名视图。三层强制：M_OPEN 协商内核 RO → 客户端 EROFS；服务端派生名逐 op 权威门禁回 E_NOTPERM；本地 --home 挂载同判。需要可写的自定义形状，用客户端自备的 mount --layout 透镜（§15.5，直写真实条目）。不是安全边界：直挂基名仍见全树，拦住他的是 token / key，不是形状。其余：define 替换热生效（逐 op 检查定义 mtime，已挂载连接 ≤2s 换形、免重挂）；view rm 不热作用（已挂者保持旧形状到重挂）；换形时旧虚拟 ino 的合成路径/fd 可能落回 ENOENT，真实条目 inode 稳定；不嵌套（base 须是物理视图）、不得与基同名、不得遮蔽物理 db。控制面位置：SQLite 部署是 meta/views/*.layout（HA 备机需随控制面库 api_keys.db/refs.db 手工同步）；PG 部署随 grovefs_control.view_defs 复制，无本地文件、无需手工同步。热重载仅限 meta-server，本地挂载挂载时解析一次。详见 §15.6。
  • 服务端纯别名 grovefs view alias：与派生视图的正反面——别名挂载全树可写，真实名被治理后不可直挂（本地与服务端均拒）。单跳解析、每 M_OPEN 重扫 views/（挂载是罕见事件）；拒别名链/派生目标/一真实名多别名；import 拒别名目标；删别名仅影响新挂载（已建立连接不受影响）。拒因随协议回传，远端与本地逐字节相同（老服务端 data 段为空时才退回通用 token 文案）。改名不是安全机制，硬边界仍是 token + 可撤销 api-key。详见 §15.8。
  • fork 视图 grovefs view fork：复制目录项（保留 ino/硬链接，不复制 ctrl/locks）成独立元数据树，内容字节经跨视图账本共享；结构写放行、内容写 EROFS——本地与 meta-server 同判，但这是客户端门（绕过 FUSE 直连 data-server 的 raw 协议仍可写字节，硬边界仍是 token + API key）。基必须是本地 SQLite 物理视图（有定义的名字不能当基；PG 不支持 fork，权威树不在文件里）；alias 拒指向 fork；view rm 删 fork 的树并 refs rebuild，已挂载的 fork 保持已解析的名字到重挂；import 拒 fork 目标。由 fork 套件 55 条断言证明。详见 §15.8.1。
  • 元数据导出/导入 grovefs view export / import：只搬 元数据树，内容字节需另拷 blocks/；导出是宿主无关 JSONL(无绝对路径/设备号/主机名/宿主 inode，blob 仅以 data_ref 引用)，因此可跨机器/跨系统迁移。导入先建临时树再原子 rename(失败不伤旧树)，完成后重建 refs.db 账本；保留 id/inode(硬链接)/mode/uid/gid/时间/符号链接文本。边界：虚拟名(别名/派生)无自己的树，拒绝导出(导其物理基)；PG 后端的树不在本地文件里，用 pg_dump/逻辑复制；多盘 --root 与条带 s<N>: 属数据分布——目标机需保留相同 root 数量/顺序或相同 data-server 数量/顺序(多盘也可合并成单 root)，否则会映射错/明确拒绝；整目录冷拷会把 HA epoch 带过去，旧主必须先停。由 migrate 套件 74 条断言证明。

智能体接口与凭据

  • 智能体接口 grovefs mcp：把视图治理以 MCP 工具暴露，与 grovefs view 共用同一套库函数（一个契约、两个入口，校验/拒因文案/落盘动作逐字节相同），智能体做不出 CLI 做不出的事、也绕不过任何守卫。控制面 only：不挂载、不读不写数据；默认信任能启动此进程的调用方，跨网准入仍由 token / API key 负责，可用 --require-api-key 可选地设门。热生效仅限 meta-server 入口。已覆盖 2025-06-18 协议的常用方法面（手写 JSON-RPC，未引框架 crate）：生命周期、tools/*、resources/*、prompts/*、completion/complete、logging/setLevel 与 notifications/message；客户端通知一律静默。读面复用同一套渲染器，结果与工具逐字节一致。未做：资源订阅（subscribe）与各面的 listChanged 推送（均声明 false）。详见 §15.9。
  • 可撤销凭据 grovefs apikey + --require-api-key：它是入口门而不是隔离墙——认证“哪个调用方开了哪扇门”（scope 分隔 mcp/mount，拒因逐字节回传，每次连接/调用归属到具体 key），但不改变治理语义本身；“谁能碰哪棵树、读写还是只读”由 --view/--ro 在服务端逐 op 强制。复证是 op 驱动的，故撤销的封停边界是“首个服务端往返”；已建立的 grovefs mcp 会话保持身份到重连。两面门都是 opt-in；--token 与它可同时存在（两道都得过）；data-server --keys-from 默认取首个 --root，分盘部署必须指对（指空则 fail-closed）。key 只存 SHA-256，控制面库（api_keys.db / PG 表）泄露不产生可用凭据；明文只打印一次，丢了重铸。详见 §15.9.1 与 §14.8 撤销演练。

数据导入与后端

  • 零拷贝导入 grovefs import：硬链接要求源与 blocks/ 同文件系统（跨盘自动退化为独立拷贝并如实计数）；外部工具以 rename/替换写更新源文件（vim 默认行为）时，视图侧保持旧 inode 的最后内容，需对新内容重跑 import（已有名字跳过，可换 --prefix 强制重登记）；symlink/特殊文件有意跳过；单文件不走 ≥16MiB 跨 server 条带；meta-server 部署下直写权威 db 文件，须在存储机执行、已挂载靠 TTL（≤2s）收敛；PG 后端不支持（走挂载点 rsync 灌入）；--source 建议与存储根同盘并保留。详见 §15.7。
  • PostgreSQL 后端与 HA 互斥:--store postgres://… 下自研 HA(--role standby / --peer / --witness)在启动时 fail-fast;backup_to_bytes 返回错误——高可用请交给 PG 自带的流复制 / logical replication / PITR,不在 GroveFS 里重一个共识。凭据与控制面状态(key/审计/视图定义)在 PG 模式下随 --store 全进 grovefs_control schema(本地不落控制面文件),一次 pg_dump 即覆盖,无需单独冷备。
  • 元数据读并行 / 目录分页的作用范围：只读连接池与 LIMIT/OFFSET 分页长在两个存储引擎（SQLite MetaEngine / PG PgEngine），各 4 连接只读池。本地 --home 吃满分页与 PLUS；meta-server 的并发处理器吃各自后端的池，M_READDIRP 帧把分页下推到服务端。仍走 trait 默认实现（每缓冲一次全量列表、不协商 PLUS）的只有 LayoutMeta 派生/透镜与对接老 meta-server 的挂载。元数据写并行已覆盖 PG（单集群 SERIALIZABLE 写池，见 §6.2）；跨节点多权威/分片的写扩展未做。判据 supports_paged_readdir() 由单测钉住。
